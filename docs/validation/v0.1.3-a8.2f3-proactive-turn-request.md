## Source boundary

Before this leaf, `POST /v1/proactive-turns/stream` parsed its strict request and immediately created the Runtime async iterator, then advanced it with the first `next()`. The Runtime method is also used by Runtime's internal proactive scheduler, so Journal admission belongs to the external HTTP adapter only. The route had no `requireLocalDashboardAccess` guard. Runtime's first advancement owns the existing eligibility, consent/activity/speech/cooldown, claim and provider decisions; none were moved into the route or receipt facade.

## Receipt and authority

`HostProactiveTurnReceiptAdmission` is constructed by AppContext over the existing `JournalRepository` and exposed beside Runtime as a narrow host-owned seam. It accepts only a bounded session correlation, `readMemory` and normalized `promptPreview`. It commits a host-built `RECEIPT/CONTROL` with a retained JSON control summary and a conversation correlation for the session. The summary contains the operation and safe booleans only; it contains no request text, assistant/provider output, auth/token/IP material or Runtime claim key.

The authority records principal and Person binding as `UNRESOLVED`, no subjects, audience `UNKNOWN`, the local route surface, an unresolved source reference, and producer version `0.1.3-a8.2f3`. No `sourceDedup` is supplied. The caller's `idempotencyKey` remains Runtime's volatile logical claim key: it is not a transport delivery identity, is not persisted or hashed into a Journal identity, and does not collapse repeated external requests. Identical requests can therefore create distinct receipts even when Runtime later rejects a repeated claim.

## Admission and disconnect ordering

The route performs local-dashboard authorization before schema parsing/admission, bounds the session correlation and idempotency key, and installs disconnect handlers before awaiting Journal append. Only after the durable append succeeds and the request remains current does the route create the Runtime stream and call `iterator.next()`. SSE hijack/headers and semantic output remain after the first Runtime event. Runtime re-evaluates its ordinary gates after commit; a later denial/conflict leaves the receipt intact.

If the client disconnects before append begins, the route starts no Runtime work. If it disconnects while PostgreSQL append is pending and the append commits, the receipt remains but currentness is checked before Runtime stream creation. If disconnect happens after Runtime starts, the pre-existing AbortSignal/iterator-close handling remains. Journal errors return a bounded 400/503 admission response and fail closed without memory fallback or automatic retry.

Internal scheduled proactive wakeups remain in Core Runtime and do not call this external route facade. Core Runtime source and scheduler ownership were not changed; the proactive scheduler regression suite passed.

# A10.1f2 Profile freshness lifecycle validation

**Status: IMPLEMENTATION PRESENT; REAL MEM0 FRESHNESS VALIDATION BLOCKED.** A10.1f2 remains **PLANNED** in the roadmap until a local Mem0 service can provide the frozen bounded COMPLETE source read. Aggregate A10.1 remains **INCOMPLETE**.

## Implemented

Migration `018_profile_lifecycle_v1.sql` adds one durable control row per enrolled strict f1 subject. It stores the monotonic control version, latest complete source observation, exact candidate tuple, bounded attempt state, lease fence and safe reason/error. SQL checks the subject/scope mirror, candidate and lease tuples, ordered versions and clean-row invariant; the candidate FK references immutable migration-017 snapshots. Migration 018 is idempotent through the existing migration runner.

PostgreSQL and process-local in-memory stores implement enrollment, invalidation, source observations, due claims, lease renewal/reclaim, fenced candidate selection, failure/release, audit pages and bounded startup recheck. PostgreSQL claim and publication use short transactions and `clock_timestamp()`; source reads and f1 generation run outside database locks. BIGINT values cross the TypeScript boundary as decimal strings. Old owners cannot renew, release or publish over a newer version/fence.

The worker uses one subject row as the coalesced job: first due at 250 ms, one claim per tick, 1 s polling, 90 s leases, 15 s heartbeat, 120 s attempt deadline, three attempts per control version and 1 s/5 s retries. It shares a serial executor with an ordered 30 s audit in batches of 100. Startup rechecks enrolled rows in bounded batches; shutdown aborts and drains lifecycle work before the shared PostgreSQL Pool closes.

Generation uses a captured reader/provider/backend composition from the same active `MemoryService`. It performs COMPLETE pre-read, the existing f1 generation read and COMPLETE post-read, requiring equal canonical source digests plus backend, composition, cancellation, control-version and lease fences before candidate CAS. f1 snapshot history and `profile_current` semantics are unchanged; the f2 CAS does not modify `profile_current`.

The scope bridge reads the exact candidate history revision, performs a new COMPLETE source read and digest comparison, rereads the lifecycle control tuple, then checks the local composition/cancellation fence immediately before returning. Mismatches withhold content and coalesce regeneration; partial, unavailable, unsupported or failed reads return no model. The projection is `yuvi-people-scope-model.v1`, carries `UNBOUND_SCOPE`, and exposes only a transient `VERIFIED_AT_SOURCE_READ` proof. Person-only access returns `BINDING_AUTHORITY_UNAVAILABLE`. `readMemory=false` and disabled Memory return no model without source/history reads; `writeMemory=false` does not revoke reads.

Legacy repository notifications run after durable effects and cover grounded admission, relevant raw updates, lifecycle/status/validity/relationship changes, archive, restore, forget/delete, and old/new partitions on moves. Memory-maintenance CLI uses the shared PostgreSQL repository seam. Mem0 add/keyed-submit/update/delete use bounded pre/finally notices; reconciliation notices use the frozen payload scope and do not change delivery outcomes. Hooks are liveness hints; notifications cannot roll back or falsify a Memory mutation. Per-component notification failure counters are available through repository, backend, provider and MemoryService diagnostics.

No HTTP/UI surface, Person binding, People.Facts write, LLM synthesis, f1 policy/ABI change, tombstone, correction authority, or second retry engine was added.

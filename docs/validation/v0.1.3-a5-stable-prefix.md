## Audit and classification

A4's sole assembly authority remains `packages/prompt-builder/src/canonical-context.ts`. Runtime obtains producer-owned P8 and Memory vNext projections, PromptBuilder policy and compatibility sections, the admitted current user text, and attached visual observations, then passes the assembled value to Character and Cognition. Cognition derives its authorized task, currently discovered 6G capability descriptions, and A3 interaction protocol through its existing projection. Runtime-retained request/observation pairs are appended only after that preamble.

The repository's legacy `PromptSection.stable` and `stable` inputs to Memory context compression are budget-preservation signals, not cache-stability authority. `CurrentTime` is marked `stable: true` by the legacy builder despite containing current timestamps. A5 derives its own classification and explicitly marks every non-policy compatibility section volatile in the A5 volatile projection.

The audit found one mixed-stability field: the production P8 adapter embedded the current speech speaker result in `IDENTITY` and changed that section's state based on current speaker evidence. Runtime now supplies the same bounded speaker result as part of volatile `CURRENT_SITUATION`, while the P8 identity projection contains only P8-owned identity semantics. This small A4 projection correction is required so current perception cannot enter stable-prefix identity. Character and Cognition still receive the current speaker result; A5 adds no voice-evidence persistence path or authority to create relationship truth.

Character's fixed generation/response schema instructions and output-language protocol remain its existing execution contract. They are path-specific and are not provider-cache metadata. The Cognition output protocol is separately present in the A5 canonical stable projection because it is already an A4 Cognition semantic input.

## Stability contract

`CanonicalContext.stability` exposes a `stablePrefix` and `volatileContext`, both derived inside the A4 assembler. Stable components retain the relative order of A4 shared identity/persona, policy, capability descriptions, and Cognition protocol. Volatile shared sections retain the A4 `IDENTITY → PERSONA → RELATIONSHIP_CONTEXT → RECENT_CONVERSATION → MEMORY_EVIDENCE → TEMPORAL_CONTEXT → CURRENT_SITUATION` order after stable-section filtering; compatibility PromptBuilder sections retain their original order. The A5 partition is metadata only: existing Character, Chat, Cognition, and provider projections continue to serialize the canonical fields in their established A4 order, so the A5 metadata itself cannot change product meaning.

Prefix identity is the exact serialization:

```text
canonical-context-stability.v1:<JSON of ordered stable component tuples>
```

The tuples encode component kind and explicit semantic values. P8 section provenance references are sorted because they are an unordered set in that projection. Capability descriptions include the validated 6G version and exact model-facing inventory; the interaction protocol includes its contract version and exact text. Policy instruction order remains the PromptBuilder order. This versioned representation is collision-free and independent of object allocation or incidental property order; it is compared internally and is not sent to provider adapters. A classification-format change requires a stability-version change. Changing only volatile context leaves the identity unchanged.

Character and Cognition use the same shared classification. Their intentional differences remain explicit: Character receives the admitted user turn and its output protocol; Cognition receives Character's bounded authorized problem, the current 6G inventory, and the A3 interaction protocol. Capability descriptions and protocol are stable Cognition-only additions; task and current multimodal/perception evidence remain volatile. `volatileContext.executionLocalComponents` identifies `CAPABILITY_REQUEST_OBSERVATION` as volatile without copying any request or observation payload; A3 retains and serializes those pairs.

The A3 continuation remains an appended suffix. Each assistant `REQUEST_CAPABILITY` is immediately followed by its matching user observation. No A5 metadata is inserted into the pair; unrelated Memory, policy, or other canonical context remains before all pairs. Different execution evidence leaves prefix identity and the pre-pair Cognition messages unchanged. Later context cannot mutate the frozen execution evidence. Successful capability output remains evidence and does not itself grant Memory or P8 write authority.

DeepSeek and OpenAI-compatible Chat/Reasoning adapters continue to serialize the supplied messages and request envelopes. xAI Vision continues to format the current image as multimodal wire content. No provider adapter makes or receives a cache-stability decision, and no provider cache behavior, header, or API was added.

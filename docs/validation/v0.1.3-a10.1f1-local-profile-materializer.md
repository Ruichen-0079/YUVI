## Implementation

The implementation adds strict scope-based Profile types and bounded source outcomes in `packages/memory/src/profile-types.ts`; repository-native and Mem0 readers in `profile-source-reader.ts`; canonical lineage, root, digest and deterministic entry materialization in `profile-materializer.ts`; immutable in-memory/PostgreSQL stores in `profile-snapshot-store.ts`; and the local explicit-generation provider in `profile-provider.ts`. `MemoryService.getProfileMemorySourceReader()` selects the currently active backend. `AppContext` composes one provider over that service and the existing shared PostgreSQL pool, or an in-memory store when no pool is configured.

`ProfileSubject` is exactly a canonical `MEMORY_SCOPE`; its optional opaque `subjectReference` adds correlation only. It does not establish authentication, authored Person identity, or a Person binding. `ProfileEvidenceSource` is strict and backend-neutral: it contains bounded content, typed claim semantics, canonical lineage and digest, lifecycle coverage, explicit relationships, and reconstructible root constraints. Arbitrary backend metadata and embeddings are omitted.

The legacy source read applies the exact user/persona partition before a deterministic ID order, performs one read-only bounded database cursor query with a 4,096-row limit plus one lookahead, a 30-second statement timeout and a 64 MiB raw bound. It does not read embeddings or update access timestamps. In-memory enumeration follows the same scope/order/row/byte rules. Content and lineage are individually capped at 65,536 bytes; normalized source sets at 16 MiB; snapshots at 64 MiB.

The additive Mem0 `bounded_snapshot` mode requires limit 4,096 and offset zero. The sidecar reads through the existing storage connection while holding the existing idempotency lock, in a read-only transaction with a 30-second timeout. Its single parameterized scoped query selects only `id` and `payload`, orders by ID, and reads 4,097 rows to prove exhaustion. Collection identifiers come only from validated existing configuration. It returns an explicit mode/exhaustion/raw-byte marker; the TypeScript adapter bounds the response stream at 64 MiB. Ordinary listing remains capped at 100 and retains its existing behavior.

`COMPLETE` requires a valid exhaustion marker and all row/byte bounds to be proven. `PARTIAL` reports a row, byte, content, lineage, or missing-exhaustion boundary. Unsupported enumeration, timeout, cancellation, disabled Memory, or unavailable backend returns `UNAVAILABLE`; malformed records/lineage, scope mismatch, conflicting source identity, or integrity failures return `ERROR`. A truncated result is never persisted.

Eligibility requires strict `memory-lineage.v1`, `GROUNDED` state, retained/selectable TEXT roots, supported direct origins/derivations, or the exact `DERIVED` + `DREAM_DERIVATION` shape with valid per-parent source snapshots. Legacy-incomplete, non-evidence, assistant-generated/inference, unsupported derived shapes, inactive/expired/future, malformed, or unavailable payloads are excluded or fail closed as specified. Legacy lifecycle and known retired roots are read from repository state. No importance, similarity, confidence, subtype, or taxonomy filter is added.

Roots bind the actual Journal event reference and selector plus each source's origin, authority, and time. Direct and Dream representations of the same receipt retain separate evidence entries when their consumer keys differ, but share one root identity, so Dream does not amplify confirmation. Dream remains `DERIVED`; no aggregate user authority, Person binding, or broad audience is invented. PRIVATE, GROUP membership (including UNKNOWN), and UNKNOWN audience constraints remain separately reconstructible. Entries preserve report/claim text verbatim and remain `UNVERIFIED`; only explicit contradiction or supersession links form symmetric conflicts. Semantic conflict is not inferred from prose.

Snapshots use strict `yuvi-profile.v1`, `narrative: null`, and materializer `a10.1f1-deterministic-evidence.v1`. Canonical sorting, exact logical deduplication, explicit conflict links, inherited constraints, and root snapshots are deterministic. `sourceSetDigest` binds the canonical normalized semantic source set, including content and grounded ancestry, independently of backend return order and `generatedAt`. `profileRevision` is `pf1_<sha256>` over schema version, materializer version, canonical subject, and source-set digest; it excludes wall-clock generation time.

Migration 017 adds immutable `profile_snapshots` and an explicit `profile_current` pointer. PostgreSQL writes serialize subject selection in one transaction; same revision/same logical payload replays the original stored snapshot, conflicting payloads fail closed, and prior revisions remain immutable. The in-memory store has the same behavior, deep-clones inputs/outputs, and serializes per-subject pointer updates. “Current” means last explicitly selected revision, not freshness.

The local ABI reports `yuvi-local-profile`, provider version `1`, `localPrivate: true`, `hosted: false`, `asyncGeneration: false`, schema `yuvi-profile.v1`, and source backends `legacy` and `mem0`; no generation-status job exists. `getProfile` reads only the store and reports freshness `UNCHECKED`. Only explicit `generate(subject)` captures one `asOf`, resolves the active source reader once, requires a complete enumeration, materializes deterministically, validates bounds, and immutably stores/selects the result. Disabled Memory may still serve a previously stored snapshot; generation is unavailable. Incomplete reads do not create a profile. Profile snapshots never feed Memory, Journal, RecentEpisode, or Dream. Product Person IDs and caller hints do not become authenticated identity.

## Scope and status

Generation does not use relevance search or `listRecentMemories` as a completeness proof. Legacy incomplete rows cannot create known entries; malformed grounded-looking Mem0 lineage cannot be silently omitted from a COMPLETE read; direct plus Dream of the same receipt shares one root; profile content never feeds the next generation; and no Product Person ID is promoted to authentication. Hosted Mem0 profile APIs remain unnecessary; local deterministic generation works.

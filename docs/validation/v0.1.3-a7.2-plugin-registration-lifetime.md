# v0.1.3 A7.2 — Plugin registration and executable lifetime

Status: **IMPLEMENTED REALITY**. This record captures the A7.2 source audit, implementation boundary and verification on `codex/v0.1.3-platform-completion-20260922`. A7.1 remains implemented; A8.1 and later atoms remain planned.

## Source audit

The audit was performed against the verified A7.1 starting commit `cb5b708ede2994866aa41c9cfe31213db5792553`, before editing.

1. **A6 lifecycle ownership.** `ServerPluginLifecycle` is the sole plugin lifecycle owner. It validates composition-supplied manifests, defers loader calls until load, starts in deterministic plugin identity order, stops in reverse start order and disposes in reverse load order. Lifecycle hooks have a 5-second bound. Its original plugin context exposed only `{ manifest, signal }`; no capability, Runtime, Memory, provider or database object was passed.
2. **A7.1 registry construction.** `mcp-capability-binding.ts` owns a branded, immutable static registry. The private approved implementation table contains only `yuvi.server.mcp.read_text_file.v1`; discovery intersects availability with `read_text_file` and cannot add bindings. Registry construction rejects duplicate capability refs and duplicate implementation refs.
3. **Implementation lifetime before A7.2.** No stable plugin executable lifetime existed. The A7.1 binding was a static tool name and delegated to the existing MCP client call; A6 had no registration handle or active capability-call count.
4. **Safe revocation point.** A plugin registration is staged during load/start and becomes visible only after successful start. Stop first changes its scope to revoked, immediately removing it from the host snapshot and preventing new admissions. Calls already admitted by Core Runtime are counted by the owning scope and retain their handler reference until settlement.
5. **Shutdown order.** Before A7.2, `server.ts` called plugin stop/dispose first, then closed maintenance/presentation, drained Memory ingestion, called `Runtime.sealAndDrainMemoryWrites()`, and closed repositories. Runtime had no general capability-call drain. A7.2 drains plugin-scoped calls inside lifecycle shutdown before stop/dispose; the existing later Memory-write drain and repository close order remains intact.
6. **Plugin import/dependency surface.** There are no production plugin packages or production `discoverPlugins` call sites. Plugins are in-process, composition-supplied sources. Therefore the enforceable supported boundary is the lifecycle context: the host can issue grant-specific registration handles, but cannot sandbox arbitrary JavaScript imports. This remains a composition-trusted model, not a hostile-code security boundary.

## Implemented boundary

The server composition root may provide versioned host grants that bind an exact plugin ID/version to a semantic capability reference, description and unique versioned implementation reference. The grant validator rejects extra fields and fixes the effect contract to `RUNTIME_ADMITTED_LOCAL_TRANSFORM`, `TRANSFORM`, `PROCESS`, local-plugin request disclosure, reversible, no idempotency claim and unsupported reconciliation. Plugins cannot set or change any of those fields.

Only the matching plugin instance receives its scoped `register(handler)` handle. It receives no registry mutator, invocation method or server services. Its declarations remain inert. Registration during load/start is staged; invalid or duplicate registration poisons and clears the scope. A failed load/start, revoked handle, version mismatch or missing host grant cannot publish an executable entry. A plugin handler returns bounded semantic text; Cognition sees only the semantic reference and description.

`executeServerCognitionInteraction` adds currently registered descriptions to the Cognition inventory. The only plugin-handler call site is Core Runtime's existing admitted capability callback, after Core has checked policy, call budget, cancellation and execution fences. The host surface is not included in plugin context. A zero-call Runtime budget is tested to leave the handler untouched.

On stop, the lifecycle revokes all registration scopes before waiting. If calls settle within the lifecycle bound, it performs reverse stop/dispose normally. If a call remains active after the bound, the lifecycle and active plugin report `DRAINING`; the server close hook returns a diagnostic snapshot and keeps the implementation and plugin instance referenced. Stop/dispose run in the background only after that call settles. A late result does not republish the registration.

This timeout disposition is bounded only for the close hook and is **in-process only**. If a call never settles, cleanup remains deferred. Process termination can destroy that in-memory unresolved state. A7.2 does not claim durable recovery, exactly-once effects, or external dispatch; those require A8/A9 work, especially A9.2.

The supported API is the injected lifecycle context only: manifest, abort signal and optional grant-specific registration handles. Tests exercise this actual context across load/start/stop/dispose and confirm it exposes no Runtime, Memory, provider, repository/database, scheduler or direct invocation service. Because A6 is composition-trusted, code that imports arbitrary modules outside the supported API remains outside the guarantee.

## Compatibility and deliberate limits

- Existing `read_text_file` registry construction, discovery filtering, Runtime route and normalized observation remain unchanged.
- A7.1's duplicate `implementationRef` invariant remains. Host policy rejects duplicate plugin semantic/implementation identities and reuse of the read-text implementation; each plugin grant has a unique versioned implementation reference.
- The static A7.1 approved implementation table remains static. A7.2 stores owner-scoped executable lifetimes in the existing plugin lifecycle host and combines only semantic descriptions at Runtime composition; it does not make plugin code able to mutate A7.1's table.
- Production composition supplies no plugin capability grants. The executable fixture is an in-process local text transform only; no remote service, durable store, physical-world effect or external dispatcher is enabled.
- Plugin `surfaces` declarations remain metadata. No UI, route or presentation surface was activated.
- Plugin code remains trusted in-process JavaScript. The handler's local-transform effect contract is host policy, not a sandbox or proof that hostile code is pure.

## Provider-facing order

`createCognitionInteractionReasoningInput` now projects:

```text
user: authorized task
user: current capability inventory
user: bounded interaction output protocol
assistant: REQUEST_CAPABILITY + validated semantic request
user: corresponding normalized capability observation
assistant: REQUEST_CAPABILITY + next validated semantic request (if any)
user: corresponding normalized capability observation
→ next generated assistant/Cognition continuation
```

Every pair is emitted together, in Runtime's execution order. No Memory, reminder, system, or presentation section can be inserted between request and observation. Repeated references remain separate ordered pairs; the serial Runtime loop has no concurrent invocation matching problem and needs no new persistent call identity.

The request uses the existing 6H validator and the execution's authorized static inventory; the observation uses the existing 6N validator and must have the same opaque reference. Unknown fields, missing halves, mismatched references, invented references, concrete arguments/transport metadata, and failure results containing purported successful content fail validation. Messages and their array are immutable snapshots.

Current discovery still governs **new** requests. A removed capability does not erase valid historical evidence; new proposals for it are rejected. The existing generic 6P observation projection carries SUCCESS content as evidence, or only the UNAVAILABLE/ERROR status. The next provider call supplies the continuation. Payload-free CONTINUE repeats over the same admitted task/evidence without injecting private reasoning or a new prompt section.

The provider-neutral interface uses existing assistant/user messages. The reserved `tool` role and vendor function-call formats remain unsupported. Runtime's A2 budgets cap the retained history, and 6N bounds each successful observation to 16,000 characters.

## Evidence, visibility and persistence rules

| Artifact | Visibility / current execution | Conversation persistence / later context | Memory and P8 authority |
| --- | --- | --- | --- |
| Semantic capability request and normalized observation | Cognition's current execution only; not a user-facing message or presentation event | Not appended to conversation or reconstructed for another turn; execution-local history is discarded after completion | Neither is submitted directly as a Memory record, P8 update or relationship truth |
| CONTINUE and Runtime counters, identity, deadline, terminal state | Runtime control only; counters/identity never become model semantics | No transcript record or durable state store | No Memory/P8 meaning or write authority |
| Raw provider reasoning, transport payloads/errors, tool/server names and authorized filesystem path | Remain outside the semantic projection; existing adapters discard/normalize them | Not persisted as conversation content or injected into subsequent context | No truth or write authority |
| Normalized terminal Cognition result | Current Character re-entry through existing 5H/Harness validation | Not itself appended to conversation; final Character expression may use its supported content | Normalization/completion alone does not establish truth |
| Final Character reply | Existing user-visible output and presentation path | Existing conversation commit and subsequent recent-conversation context rules apply | Existing write consent, finalized-turn admission, Memory extraction/validation and P8 interpretation remain authoritative |

A final reply can express facts derived from evidence. The distinction is that a successful capability call does not directly create a durable fact: any later Memory/P8 interpretation still crosses its existing authority. These rules do not promise that all successful observations are factually correct or immune to model misinterpretation.

## Focused source audit

The audit was performed on the verified target tree before source edits.

1. **PostgreSQL process ownership.** `DesktopSupervisor` owns the existing PostgreSQL service lifecycle and packaged private-cluster configuration. It starts the existing daemon through the Supervisor service graph; Runtime does not start PostgreSQL. Packaged Linux staging already copies the supported PostgreSQL distribution and the existing migration directory. No process, data directory, port, daemon configuration, or Supervisor owner was added.
2. **Database configuration.** Runtime receives the configured database URL through `DATABASE_URL`. Supervisor also passes that configured URL to the Mem0 sidecar as `MEM0_PG_CONNECTION_STRING` when applicable. `MEMORY_REPOSITORY` selects the legacy PostgreSQL or in-memory repository; `MEMORY_BACKEND` independently selects legacy Memory or Mem0.
3. **Pool ownership before this leaf.** `PostgresMemoryRepository` created its own `pg.Pool`. Conversation and finalized-ingestion repositories could share the Memory repository's pool only when PostgreSQL Memory was selected. Recent-episode and Dream stores each had their own constructor-owned pool in their PostgreSQL mode. There was no backend-neutral Pool factory/owner that Journal could use without constructing PostgreSQL Memory.
4. **Migration ownership.** `packages/memory/src/migrations.ts` is the existing SQL catalog/runner: it reads sorted `*.sql` files and executes them sequentially, with no parallel migration framework or tracking table. Existing migrations use idempotent DDL. The desktop package copies `packages/memory/migrations` into Runtime resources, and the packaged Runtime entry invokes this same runner.
5. **Mode behavior.** With `MEMORY_REPOSITORY=postgres`, the configured database was already used by the legacy Memory repository and related configured PostgreSQL repositories. With `MEMORY_BACKEND=mem0`, the Mem0 semantic backend is independent of that legacy repository choice; the sidecar may use the same Supervisor-owned PostgreSQL service. Before this leaf, choosing an in-memory legacy repository left no shared Runtime Pool for a Journal. Packaged Runtime migration was also gated on the legacy PostgreSQL repository selection.
6. **Infrastructure seam.** No generic database package existed. A small `packages/database` factory is now the sole shared Runtime Pool constructor. `AppContext` owns one Pool when `DATABASE_URL` is configured, injects it into repositories configured for PostgreSQL, and closes it once after service drains and repository facades close. Those facades do not close an injected Pool. Journal receives this Pool regardless of `MEMORY_REPOSITORY` or `MEMORY_BACKEND` selection. The existing Windows localhost normalization and 10-second connection timeout are preserved.
7. **Journal contract owner.** `packages/protocol/src/life-event-journal.ts` remains the semantic contract owner. `packages/journal/src/index.ts` is the PostgreSQL append/reconstruction adapter. It does not make Memory the Journal owner and does not mint source identities or authenticate transports. AppContext has a fail-closed host authority builder until ingress leaves supply real host-verified evidence; no production route calls Journal in A8.2a.
8. **Identity compatibility.** Existing Memory event IDs, Mem0 UUIDs, `sourceTraceId`, conversation message IDs and Runtime IDs remain source/correlation identifiers. Journal IDs are separately generated and satisfy the A8.1 `JOURNAL_EVENT` reference format.

## Implemented store boundary

Migration `013_life_event_journal_v1.sql` adds five explicit tables: `journal_namespaces` for the per-namespace sequence lock/state; `journal_events` for the versioned committed envelope; `journal_event_parents` for same-journal parent foreign keys; `journal_payloads` for immutable payload descriptors and retained text only; and `journal_source_dedup` for scoped source identity and payload-digest equality. The envelope remains versioned JSONB, while relational keys/checks enforce namespace, event identity, sequence, parent existence and payload identity/retention consistency. The existing SQL migration catalog discovers the new migration by filename and its idempotent DDL safely reapplies.

`PostgresJournalRepository.append` accepts an A8.1 producer command, candidate payload descriptors, optional retained text and an optional host-normalized stable source key. It rejects extra top-level authority fields and validates the strict A8.1 command. A host-configured authority builder creates the separate authority snapshot; the repository supplies its configured namespace and assigns a cryptographically opaque `jev1_` event ID, host recording time and sequence. The A8.1 validator constructs the committed envelope. Callers cannot provide the committed envelope or override those fields.

Each append runs one transaction. It creates the namespace state row if absent, locks that row with `SELECT ... FOR UPDATE`, and holds the lock through parent/dedup checks, envelope/payload/parent/dedup inserts, sequence advancement and `COMMIT`. The next append cannot read/assign the next sequence until the transaction holding the lock has committed or rolled back. Thus `commit_seq` represents actual serialized visibility order, not a preallocated PostgreSQL sequence or wall-clock order. A rolled-back append leaves no event, payload, dedup identity or sequence advancement.

Before insert, each causal parent must be in the configured namespace and present in committed history. The A8.1 kind/parent validator checks direct relationships, and the repository requires each parent sequence to be lower than its new child's. PostgreSQL composite foreign keys enforce same-journal parent existence. Since new local events may reference only already committed events, this append path cannot introduce a local causal cycle. Cross-journal/imported history remains unsupported. Full ancestry validation is available only to A8.1's complete-history fixture seam; A8.2a does not claim a database-backed global graph audit.

Deduplication is optional and RECEIPT-only. Its unique identity is `(journal namespace, source namespace, source key)`; SHA-256 of the trusted adapter's normalized payload is only the equality/conflict check. Same key and digest returns the existing committed receipt, same key with a different digest fails with `SOURCE_DEDUP_CONFLICT`, and absence of a stable source identity always appends a new event. Text/content hashes alone never deduplicate.

Payload descriptors retain A8.1's explicit retention states. Only retained TEXT is stored as payload content, with immutable payload namespace/ID/version, descriptor, character bounds and SHA-256. A matching already committed TEXT payload can be reused only with the same descriptor. `get` and `resolveRetainedText` reconstruct from PostgreSQL after reopen and reject relational/envelope disagreement or retained-text digest mismatch. `REDACTED`, `NOT_RETAINED` and `UNAVAILABLE` content is not stored; retained AUDIO, IMAGE, JSON and TOOL_RESULT bytes are rejected in this leaf, so no raw-media archive is introduced.

Typed `JournalStoreError` codes distinguish unavailable PostgreSQL, transaction failure, invalid/unsupported proposals, unknown or cross-namespace parents, parent-order failure, source-dedup conflict, payload persistence failure and unsupported cross-namespace history. There is no in-memory durability fallback and no unbounded retry.

## Real PostgreSQL verification

The integration suite uses the reachable PostgreSQL test database, creates an isolated schema per suite, reads migration `013` through the existing SQL migration catalog, and applies it through the existing runner. It exercises real transactions and reconstruction rather than a fake repository.

- Clean migration and safe reapplication create all five Journal tables.
- All seven A8.1 event kinds append with committed envelopes; reopen reconstructs the assigned identity, namespace, sequence and recording time.
- Producer attempts to supply committed authority fields and unsupported command versions reject; a wrong namespace reference cannot retrieve an event.
- Unknown/cross-namespace parents reject; committed parent foreign keys and lower sequence are checked.
- A forced PostgreSQL insert failure rolls back event, dedup row and sequence advancement.
- Stable scoped key/digest reuses the same receipt; changed digest conflicts; equal text without a source key creates separate events.
- Retained TEXT and selector bounds survive repository reopen; `NOT_RETAINED` and `UNAVAILABLE` remain content-free; retained raw image content is refused.
- Mem0-selected configuration with `MEMORY_REPOSITORY=in-memory` can append/read Journal without constructing PostgreSQL Memory.
- Memory, conversation, finalized-ingestion, recent-episode, Dream and Journal repositories share an injected Pool; closing repository facades leaves it usable, then the owner closes it once.
- Unreachable PostgreSQL returns a typed database-unavailable failure.
- **Commit-order inversion test:** transaction A is paused by a deterministic advisory-lock trigger during its event insert while it holds the namespace row lock. The test observes transaction B waiting on the `current_seq` row lock and confirms neither event is visible. After A is released, both settle with A at sequence 1 and B at sequence 2. A nextval-only implementation would let B commit while A is paused and fail this test.

Packaged Linux lifecycle smoke used the existing bundled Runtime and Supervisor-owned database path. Runtime's bundled entry applied all 13 sorted SQL migrations twice with `YUVI_PACKAGED=1`, a configured `DATABASE_URL`, and `MEMORY_REPOSITORY=in-memory`; migration `013` was present on both runs. A committed Journal event was appended between the migration-only Runtime processes and reconstructed from a newly opened repository after the second process. This proves schema upgrade/restart persistence without a second daemon or PostgreSQL Memory repository. The Mem0 sidecar retains its existing URL/config path; no Memory semantics changed.

## Roadmap-vs-source findings and limits

- The existing migration catalog is located under `packages/memory`, even though it now serves Journal and other PostgreSQL consumers. This leaf intentionally extends that catalog instead of creating a second migration runner or moving unrelated migrations.
- Before A8.2a, `PostgresMemoryRepository` was the only generic Runtime source of a shared Pool. A small `packages/database` seam and AppContext ownership were required to make Journal available with Mem0/in-memory legacy Memory. No PostgreSQL process or credential owner changed.
- A8.2a has a storage authority but no production source/admission authority. The current AppContext builder deliberately throws until an ingress leaf can provide authenticated principal, audience, source key and payload evidence; this prevents fabricated receipts and does not claim input is durable before processing.
- Structural local parent existence/order is durable and checked now. Transport authentication, append-before-processing route wiring, source-specific idempotency, ingress reconciliation and production admission are A8.2b–f. Durable intent uniqueness, attempt/outcome dispatch fencing and reconciliation remain A9. Memory/P8 lineage work remains A10.
- A8.2a assigns recording time but does not infer causality from time. The store does not resume Runtime executions after restart, allocate A2 deadlines, or claim exactly-once effects.
- Only retained text payload content is supported here. Raw audio/image retention, deletion/crypto-shredding policy, full import semantics and production receipt adapters remain future work.

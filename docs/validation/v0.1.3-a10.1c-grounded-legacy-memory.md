# A10.1c — Grounded legacy Memory writes validation

**Status:** IMPLEMENTED REALITY
**Starting HEAD:** `07fe46e1215f490ed8f57b16f85b1719cf08caf2`
**Implementation scope:** new evidence-backed writes to the legacy Memory repository only.

## Source audit and defect closed

Before this leaf, A10.1b attached the host-derived `sourceJournalRef` to Runtime user events and persisted it on conversation rows, but Runtime's `maybeStoreMemoryInternal()` called `processCandidateForStorage(candidate)` without that ancestry. `MemoryService` then admitted and stored a legacy candidate without resolving a Journal parent, selector, or payload. Dashboard candidate acceptance could use `skipAdmissionPolicy` and a public patch, and the generic Memory creation path did not distinguish manually authored/non-evidence rows from evidence-backed writes.

The implemented path is now:

```text
Runtime user/voice event
  → host-owned sourceJournalRef + exact source text
  → MemoryService
  → JournalMemoryGroundingResolver resolves committed parent and selector
  → exact retained-text equality check
  → candidate policy/admission
  → atomic grounded Memory repository write
```

The resolver is owned by `packages/memory` behind the `MemoryGroundingResolver` / `CommittedJournalEvidenceReader` seam. Production AppContext supplies the existing `PostgresJournalRepository`; no second Journal or evidence store is introduced. The candidate, extractor, caller, and dashboard patch do not receive Journal read authority or write lineage fields.

## Contract and authority

The stored contract is versioned `MemoryLineageV1` (`memory-lineage.v1`) with `GROUNDED`, `PAYLOAD_UNAVAILABLE`, and `LEGACY_INCOMPLETE` states. New factual writes succeed only as `GROUNDED`; unavailable payloads cannot authorize a new factual row. Old rows retain null lineage and read through `getMemoryLineageState()` as `LEGACY_INCOMPLETE`; there is no text, trace, timestamp, or session-based backfill.

For each new evidence-backed candidate, the host resolver:

- validates the typed `JournalEventRef`, expected namespace, exact committed envelope ID/namespace, and existing event;
- accepts only committed `RECEIPT` parents classified as `ATTRIBUTED_ASSERTION` or `DIRECT_OBSERVATION`;
- uses only a committed `TEXT` selector and matching payload descriptor with `RETAINED`, `selectable: true`, and eligible `USER_INPUT` or `EXTERNAL_RESULT` origin;
- resolves payload text through the Journal repository, validates the descriptor again, applies Unicode code-point bounds, and requires the selected text to equal the exact source text passed to extraction;
- rejects missing/unknown parents, control receipts, unavailable/nonselectable payloads, unresolved selectors, and source-text mismatch with typed grounding rejection codes.

No similarity, substring, embedding, model judge, `sourceTraceId`, or candidate provenance is used as grounding. Attached images and raw audio do not become retained evidence through an accompanying text turn.

Origin is host-derived from the committed receipt and payload: `ATTRIBUTED_ASSERTION` plus `USER_INPUT` becomes `USER_ASSERTION`; `DIRECT_OBSERVATION` plus `EXTERNAL_RESULT` becomes `EXTERNAL_OBSERVATION`. A speech transcript remains an observation, not authenticated speaker identity. The receipt's principal, Person binding, and audience snapshots are copied unchanged; unresolved remains unresolved. Compatibility `subjectUserId`, `personaId`, `speakerId`, `voiceProfileId`, acoustic match, and display fields do not resolve lineage authority.

The committed `recordedAt` anchors Memory observation time. The committed `occurrenceTime` is copied exactly; `UNKNOWN` remains unknown. Existing deterministic temporal parsing may still derive Memory temporal fields from source text, but it does not rewrite the Journal occurrence time. Candidate-provided observation clocks do not replace committed recording time.

## Persistence and replay

`MemoryLineageV1` is persisted in `memories.memory_lineage` JSONB, with `lineage_consumer_key`, `lineage_payload_digest`, and optional explicit `evidence_classification` columns. Migration `015_memory_lineage_v1.sql` is idempotent, leaves old rows null, checks the grounded-row shape and digest, and adds a partial unique index on non-null consumer keys.

The consumer key is deterministically derived by host code from the exact Journal parent, policy version, and normalized logical candidate fingerprint. Same key and same digest returns the original row; same key with a different digest raises `MemoryLineageConflictError`. PostgreSQL performs insert-on-conflict against the partial unique index and reloads the existing row for digest comparison. The in-memory repository implements the same replay/conflict behavior.

Grounded lineage is immutable under `MemoryService.updateMemory()` content changes. A correction produces a new grounded row from the new receipt and uses existing supersession relations; the old row's lineage is not rewritten. Dashboard acceptance retains the original grounding context in private Runtime state, rejects content changes, and re-runs grounded admission; a request cannot supply a parent, selector, consumer key, or lineage.

Direct manual/admin and synthetic writes use explicit `NON_EVIDENCE`; generic evidence-backed candidate APIs fail closed without a grounding context/resolver. The `/memory` manual route marks its writes `NON_EVIDENCE` and remains within the A8.2f5 development-only authority boundary. Runtime's former no-service fallback no longer calls an ungrounded `rememberCandidate` writer.

## Semantic coverage and source deviations

- **Explicit remember:** remains available when grounded by the current utterance's exact committed selector.
- **Correction:** the new correction is grounded by its current receipt; it may supersede an older `LEGACY_INCOMPLETE` row without fabricating ancestry for that row.
- **Assistant paraphrase:** assistant-only restatements do not gain user evidence from an unrelated receipt.
- **Hearsay:** lineage establishes that the user reported the statement, not that it is true. Existing claim classification preserves `EXTERNAL_CLAIM`; claim admission normalizes external claims to unverified when represented as semantic Memory events. Legacy row metadata does not independently verify the world claim.
- **Speech:** actual STT transcript receipts classified `DIRECT_OBSERVATION`/`EXTERNAL_RESULT` resolve as `EXTERNAL_OBSERVATION`; mock-text-only speech preserves its A8.2c `ATTRIBUTED_ASSERTION`/`USER_INPUT` classification. Current Runtime policy disables legacy Memory writes for voice turns without a governed subject, and `scopeVoiceTurn()` strips caller identity hints; this leaf does not loosen that gate. The resolver supports the committed distinction, but this validation does not claim all finalized speech turns now write legacy Memory.
- **Mem0:** no Mem0 ingestion, sidecar, metadata sanitizer, or dependency behavior changed. Runtime's existing Mem0 path continues to use `storeConversationTurn` and skips legacy candidate storage; finalized Mem0 lineage remains A10.1d.
- **Other write surfaces:** `MemoryService.remember()` is explicit `NON_EVIDENCE`; manual `/memory` rows are explicit `NON_EVIDENCE`; legacy candidate processing/remembering requires committed grounding. The exported `LegacyMemoryBackend` adapter is not constructed by current production AppContext (production constructs the Mem0 adapter only when Mem0 is selected); current server legacy writes go through `MemoryService`. Direct profile-evidence writes remain an A10.2 controller/Person lineage item. No A10.2 route or schema was changed.

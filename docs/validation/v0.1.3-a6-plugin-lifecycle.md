# v0.1.3 A6 — Minimal plugin manifest and lifecycle

## Existing ownership and selected boundary

RuntimeOrchestrator remains the sole Runtime execution, interaction-round, cancellation, sealing, and draining authority. The A2 loop still admits only its bounded Runtime-owned interaction; the A3 capability evidence still belongs to that execution. A6 does not pass Runtime, Cognition, provider routing, Memory, P8, Character, or canonical context into plugins.

`apps/server/src/server.ts` owns server composition through `buildServer`, Fastify `onReady`, and Fastify `onClose`. `apps/server/src/context.ts` constructs the application services. Startup finishes constructing Runtime and routes before `onReady` discovers, loads, and starts plugins. The existing close hook now stops and disposes plugins first, then follows its prior order: maintenance scheduler, presentation bridge, ingestion coordinator shutdown, Runtime memory-write sealing/draining, then finalized-ingestion, Memory, and conversation repositories. Plugin code receives only its frozen manifest and an abort signal.

DesktopSupervisor and the Tauri exit path continue to own desktop/server-child shutdown. A6 introduces no desktop process, supervisor, or lifecycle authority. The current capability path remains the explicit server 6K MCP allowlist intersected with currently listed MCP tools, projected to Cognition's validated 6G descriptions and admitted/executed by Runtime. Manifest capability declarations are not connected to this path.

The existing MCP client and server capability binding are integration seams, not plugin lifecycle owners. The Vite daily-status plugin is build tooling and unrelated. No application plugin directory or plugin configuration authority exists; the existing runtime environment directory belongs to runtime settings and is not scanned. A6 therefore uses composition-registered `ServerPluginSource` values passed to `buildServer`. Discovery inspects their data manifests and never calls their deferred loaders. This avoids arbitrary directory scanning and network discovery.

`apps/server/src/plugin-lifecycle.ts` is the narrowest natural owner: the lifecycle boundary is server-composed, and putting it in Runtime or Cognition would transfer ownership inappropriately. `buildServer` creates one manager. Its `onReady` hook explicitly runs discover → load → start; the existing `onClose` hook explicitly runs stop → dispose. There is no plugin-owned startup, Runtime reference, execution loop, capability registry, process supervisor, or second Runtime.

## Manifest and discovery contract

Manifest v1 accepts only these fields:

| Field                                     | Validation and meaning                                                                                                                      |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `manifestVersion`                         | Required exact integer `1`; unknown manifest versions fail closed.                                                                          |
| `id`                                      | Required lowercase identity token, at most 128 characters.                                                                                  |
| `version`                                 | Required opaque release token, at most 64 characters; A6 does not parse or resolve release versions.                                        |
| `compatibility.apiVersion`                | Required positive safe integer. The host accepts exact API version `1`; any other version is diagnosed as incompatible and is never loaded. |
| `capabilities`                            | Optional, at most 64 unique declaration IDs. Metadata only.                                                                                 |
| `surfaces.presentation`, `surfaces.input` | Optional, at most 64 unique declaration IDs per list. Metadata only.                                                                        |

Unknown fields are rejected. Objects must be plain data objects; accessors, malformed declaration arrays, duplicate declarations, invalid tokens, missing fields, and unsupported manifest versions fail validation. Validated metadata and snapshots are frozen. Plugin `version` remains an informational token; compatibility is the exact host API contract, not semver resolution or dependency solving.

Composition discovery is bounded to 32 registered sources and has a 5-second deadline. Overflow is summarized with one diagnostic; excess sources are not inspected or loaded. Results are ordered by lowercase plugin ID using code-unit ordering, with source index as a tie-breaker; malformed entries sort after identified plugins and retain their source index. Every source with a duplicate ID in the considered set is rejected. A malformed/incompatible source does not stop discovery or load of unrelated compatible sources. Source-discovery failure produces a bounded warning and an empty plugin set. Manifest validation is side-effect-free and loaders are not called until the separate load phase.

## Lifecycle and containment

The manager exposes product-level phases `NEW → DISCOVERED → LOADED → STARTED → STOPPED → DISPOSED`; invalid transitions throw. Individual plugin states additionally distinguish `INCOMPATIBLE`, `REJECTED`, and `FAILED`. Load and start are explicit, occur in deterministic plugin-ID order, and are attempted only for unique compatible sources. A load/start failure or timeout records a phase-specific diagnostic, leaves that plugin out of the successful state, and does not prevent other eligible plugins from proceeding.

Each load, start, stop, and dispose hook has a 5-second deadline and receives an `AbortSignal`. Stop is attempted for each start-attempted plugin, including a plugin whose start failed, in reverse start order. Dispose runs for every successfully loaded plugin in reverse load order, including loaded-but-never-started plugins. Cleanup continues after a stop/dispose failure. Disposal is terminal: the host releases its instance reference, reports failures, and will not restart the disposed manager. Discovery→load→dispose and discovery→load→failed-start→stop→dispose both have covered semantics. Plugins are composition-trusted in-process modules in A6; the boundary provides no arbitrary remote code loading or general sandbox. Hooks are expected to honor cancellation and release resources through stop/dispose.

Diagnostics include phase, stable code, plugin ID where known, and source index where useful. They intentionally omit exception payloads so arbitrary plugin error text cannot leak secrets. Invalid manifests report a stable validation message; lifecycle failures identify the plugin and failed phase. The server logs these warnings and continues startup/shutdown after isolated failures.

Every A6 plugin source is optional; the manifest has no `required` flag because A6 adds no required-plugin policy authority. Discovery, compatibility, load, and start failures therefore omit only that plugin and do not block server readiness. Stop/dispose failures are warnings while the host continues cleanup and releases references. A loader that fails or is cancelled before returning an instance must clean up its own partial allocations; after it returns an instance, the host owns the stop/dispose calls.

## A7 boundary and untouched authorities

`capabilities` and optional surface arrays survive parsing as frozen declarations and are visible only in the plugin lifecycle snapshot/context. The load/start context has only `manifest` and `signal`. The plugin manager has no registration, dispatch, route, provider, or Runtime admission API. Tests verify manifest declarations do not alter the existing server capability binding, Cognition-visible inventory, or A5 stable-prefix identity. No `REQUEST_CAPABILITY` path can invoke a plugin. Optional presentation/input declarations attach to no route and create no additional inbound Runtime path.

No A4/A5 source or semantics changed. Canonical context, stable-prefix identity, providers, Character/P8, Memory, Runtime containment, provider routing, and desktop lifecycle remain owned by their existing authorities. A6 adds no marketplace, package-manager, signing, sandbox, hot-update, or external-surface system.

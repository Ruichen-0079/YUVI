## Implemented receipt boundary

`HostProductControlReceiptAdmission` in `apps/server/src/product-control-receipt-admission.ts` is exposed through AppContext as `ProductControlReceiptAdmission`. Its strict discriminated input union contains only configuration-save revision, a verified/preallocated Person target plus requested-primary flag, or proactive-resume operation. The facade receives no raw request object/body, Product writer, Memory provider, Runtime, provider client or raw Journal repository from a route. It uses the existing `JournalRepository.appendWithHostAuthority` API.

Each accepted operation commits an A8.1 `RECEIPT` with `receiptClass: CONTROL`, an operation-specific LOCAL surface reference, unknown occurrence time, unresolved principal and binding, no subjects, unknown audience, unresolved disclosure policy and unresolved source identity. No `sourceDedup` is supplied. The local guard does not upgrade localhost or a development token into actor identity.

The facade stores only a bounded host-generated retained TEXT summary with a fresh immutable payload reference and exact Unicode selector bounds:

- Configuration: operation and expected revision only. No API keys, provider IDs, provider URLs, model details, secret-bearing diff or full request/configuration is written.
- Person create/update: operation, target Person ID and requested-primary flag. A create UUID is allocated before append; an update ID is taken only from the verified existing Product row. Display name, notes and persona value are omitted. The Person target is not put in authority `subjects` and does not become the controller principal.
- Proactive resume: operation marker only.

No dedup is inferred from equivalent commands, revision, Person ID, configuration/text hash, request content, local address or timestamp. The receipt means only that YUVI accepted the locally authorized request for processing. No OUTCOME or DERIVATION is appended.

## Ordering and partial failures

Configuration admission runs inside the existing Product queue. A strict top-level request schema validates required configuration/revision fields before state lookup; the route checks the expected revision, clones current Product state, normalizes and validates the candidate and builds the provider registry without mutating durable/live Product settings. It then awaits Journal commit while still holding the queue and only then enters the existing `persistApply` path. Two concurrent same-revision saves cannot both be admitted: the second waits, reads the committed newer Product revision and returns the existing 409 conflict without a receipt.

Person admission also runs in the existing queue. The route validates the body, verifies update target and persona preconditions, preallocates the create ID if needed, commits the safe receipt, and only then mutates the cloned Product state and calls existing `persistApply`. The existing Memory `persistProfileEvidence` call remains after save. If it fails, the receipt and saved Person remain and the existing `profileEvidence` result is returned; there is no Journal OUTCOME/DERIVATION or automatic retry.

Proactive resume commits its minimal CONTROL receipt before calling `Runtime.resumeProactiveNow()`. A Journal admission failure prevents all three operations with a bounded response and no in-memory fallback. Database details, SQL, connection strings, tokens, provider URLs, keys and private Person fields are not included in the error response.

Once a receipt commits, later Product file/reload/packaged-speech/Memory partial failures do not remove it. This is admission evidence, not a transactional multi-store success record. No request-disconnect cancellation contract was added; downstream work follows the routes' current behavior if a connection closes after receipt commit.

## Projection protocol and authority

`POST /v1/proactive/consent` now accepts exactly one strict request form:

- `READY { revision, enabled }` — a current persisted Desktop settings view;
- `UNKNOWN_DENIED { revisionFloor }` — settings authority is unavailable or invalidated and Runtime must deny until a sufficiently current view arrives.

The route applies `requireLocalDashboardAccess` before parsing/mutation. This establishes local route authorization only. Principal and Person binding remain unresolved, subjects are empty, and audience is unknown.

`HostProactiveConsentReceiptAdmission` accepts only normalized `enabled` and `settingsRevision`. A READY projection that would establish or change current consent passes Runtime read-only preflight, commits a host-built `RECEIPT/CONTROL` summary, then revalidates and applies to Runtime. The summary identifies a settings projection, not a user-authored HTTP command. It does not persist a token, IP, or identity hint. Revision is only an ordering fence; no Journal `sourceDedup` key is used. Exact current revision/value replay is a no-op without another receipt; same-revision changed value conflicts, and stale READY is rejected before admission.

`UNKNOWN_DENIED` immediately advances Runtime's volatile revision floor and clears/prevents scheduled proactive eligibility. It does not wait for PostgreSQL, append a receipt, or persist `consentEnabled=false`. If a newer invalidation arrives while a READY append is pending, the receipt remains committed but the post-commit Runtime recheck treats the READY as stale and cannot re-enable consent.

Production AppContext requires a current projection. It ignores legacy `consentEnabled` in old Runtime policy snapshots, starts UNKNOWN_DENIED, and omits consent from later policy snapshots. Runtime policy persistence continues to own suppression and eligible-after state. Runtime replacement within a live server process adopts the current volatile projection; a process restart returns to UNKNOWN_DENIED until Web Main projects a fresh SettingsView. The projection is never reconstructed from Journal.

Web Main sends READY only when the reducer accepts the returned SettingsView at its current revision. Settings read failure and proactive `settings.changed` invalidation send UNKNOWN_DENIED. A stale view rejected by the reducer does not send READY.

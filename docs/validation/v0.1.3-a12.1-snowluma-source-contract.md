## Evidence established from source

### 1. Public OneBot message ID is locally generated and collision-prone

`packages/onebot/src/message-id.ts` implements `hashMessageIdInt32(sequence, sessionId, eventName)` by hashing a string key with SHA-1 and reading the first signed 32 bits.

Pinned source:
https://github.com/SnowLuma/SnowLuma/blob/0591b160fb913131bece693eefd1d0a2ee5a1bbb/packages/onebot/src/message-id.ts#L15-L23

An isolated source-import probe found a same-group collision between distinct sequences. Therefore public `message_id` is not accepted as a globally unique or collision-free YUVI source identity.

### 2. System-message dedup does not establish ordinary-message dedup

`packages/protocol/src/msg-push/sysmsg-dedup.ts` implements a process-local capacity-1024 set/ring for specific proven system-message routes and fails open when identity is incomplete or the route is unsupported.

Pinned source:
https://github.com/SnowLuma/SnowLuma/blob/0591b160fb913131bece693eefd1d0a2ee5a1bbb/packages/protocol/src/msg-push/sysmsg-dedup.ts#L12-L83

This is not evidence of general deduplication for ordinary inbound private/group chat and does not survive process restart.

### 3. Positive send response has limited meaning

The ordinary send path builds `MessageSvc.PbSendMsg`, waits for a hook response, decodes `SendMessageResponse`, rejects nonzero native result, then returns a SnowLuma `SendMessageReceipt`.

Pinned source:
https://github.com/SnowLuma/SnowLuma/blob/0591b160fb913131bece693eefd1d0a2ee5a1bbb/packages/core/src/bridge/apis/message.ts#L373-L493

Source establishes that SnowLuma received and accepted a successful decoded native response. It does not establish QQ durable persistence, recipient-device receipt or human read.

### 4. Ordinary send has no effective caller-controlled remote idempotency

The inspected path generates local request/random/client-sequence material. No caller idempotency key was found that the remote QQ effect honors to suppress duplicate sends.

A7 mapping under this pin:

`idempotency = UNSUPPORTED`

for ordinary private/group send.

### 5. Lost-response send has no authoritative reconciliation path

`packages/bridge/src/qq-hook-client.ts` correlates local request/ACK/reply state and times out/throws when ACK/reply does not arrive. On ambiguous response loss there is no source-backed remote reconciliation that can prove whether the QQ effect happened.

Pinned source:
https://github.com/SnowLuma/SnowLuma/blob/0591b160fb913131bece693eefd1d0a2ee5a1bbb/packages/bridge/src/qq-hook-client.ts#L616-L711

OneBot `get_msg` reads SnowLuma local stored message data; it is not an authoritative query for whether an ambiguous response-lost send took effect remotely.

Pinned source:
https://github.com/SnowLuma/SnowLuma/blob/0591b160fb913131bece693eefd1d0a2ee5a1bbb/packages/onebot/src/actions/message.ts#L114-L131

A7 mapping under this pin:

`reconciliation = UNSUPPORTED`

for lost-response ordinary private/group send.

### 6. Reconnect and audience limits

Source analysis established no downstream WebSocket guarantee for missed-event replay after reconnect. Group-member lookup is not treated as an exact receipt-time membership snapshot. QQ account/sender identity remains transport principal information, not a YUVI Person binding.

## Required YUVI semantics

For ordinary SnowLuma private/group sends:

| Dimension | `send_private_msg` | `send_group_msg` |
| --- | --- | --- |
| effect locus | `REMOTE_SERVICE` | `REMOTE_SERVICE` |
| reversibility | `UNKNOWN` | `UNKNOWN` |
| disclosure | `REQUEST_TO_REMOTE_SERVICE` | `REQUEST_TO_REMOTE_SERVICE` |
| idempotency | `UNSUPPORTED` | `UNSUPPORTED` |
| reconciliation | `UNSUPPORTED` | `UNSUPPORTED` |

The required ambiguous-send disposition is:

```text
ATTEMPT exists
OUTCOME = UNKNOWN
NO AUTOMATIC RESEND
```

Timeout/connection loss is not proof of failure.

## A12.2 constraints proven early

The future adapter must not:

- deduplicate ordinary input solely by public OneBot `message_id`;
- claim globally unique message identity from that 32-bit handle;
- equate local request/echo identity with remote idempotency;
- equate a positive native response with recipient/human delivery;
- auto-resend an ambiguous timeout/lost-response send;
- use SnowLuma local `get_msg` as lost-send reconciliation;
- treat fetched member lists as exact receipt-time audience snapshots without stronger evidence;
- treat nickname/group card as Person authentication.

## Remaining PROBE_REQUIRED items

The following remain live-probe questions rather than source-established guarantees:

1. exact QQ-side meaning of a positive native send reply;
2. native ordinary-message redelivery and native ID stability across reconnect;
3. deliberately lost send reply / connection-loss behavior with independent remote observation;
4. downstream outage/reconnect observations;
5. practical group-membership freshness;
6. practical multi-account endpoint binding.

These probes are intended to narrow `UNKNOWN`; they are not required to re-prove source-established negative capabilities such as absent remote idempotency/reconciliation under this pin.

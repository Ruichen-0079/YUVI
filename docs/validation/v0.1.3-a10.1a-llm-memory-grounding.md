## Reproduced defect

Before the fix, a deterministic reasoner received user text `The weather is nice today.` and assistant text `Okay.` It proposed `User strongly prefers astronomy.` with high confidence, `originRole: user`, unrelated weather text as evidence metadata, `sourceTraceId: forged-trace-999`, and model-selected observed/event/validity times. The old extractor assigned user origin, accepted the model trace and clocks, and provenance enrichment could use the entire unrelated user message as evidence. The legacy MemoryService admitted and durably stored the unsupported astronomy preference.

## Implemented boundary

When `MEMORY_EXTRACTOR=llm`, `LlmMemoryExtractor` no longer invokes the reasoning provider. It delegates candidate production to the existing conservative `RuleBasedMemoryExtractor`; therefore model-generated content, role declarations, traces, clocks, scopes, and metadata cannot enter the candidate or provenance path. The MemoryService storage regression exercises the actual in-process extraction/admission/repository path and confirms that the hostile astronomy proposal creates no durable row.

For configured LLM mode, diagnostics keep `mode: llm` but report `active: fallback-rule-based`, `fallbackUsed: true`, and a bounded `unsupported-grounding` skipped reason. This is not reported as a provider failure or as successful LLM admission. No provider attempt timestamp is recorded because no request is made. Disabled and unconfigured LLM selections retain distinct fallback reasons. There is no committed Journal selector grounding at this boundary; that begins with A10.1b and later leaves.

Configuration now has one strict shared `parseMemoryExtractorDriver` rule: unset and `rule-based` select rule-based; `llm` selects the safe adapter; every other value, including an empty string, rejects. Server boot and runtime reload use this parser. Runtime settings validation also rejects unsupported/empty values before applying settings; reload validates before constructing or replacing the live Runtime.

The Mem0 path still skips legacy extraction. `MEMORY_BACKEND=shadow` is retired/unsupported and resolves to legacy; if LLM extraction is also selected, it uses the safe rule-based adapter. Memory-disabled `writeMemory: false` behavior is unchanged. No Journal, Mem0 lineage, P8 authority redesign, model-tier router, or escalation policy was added.

## P8 qualification

The reproduced legacy row could contaminate legacy Memory retrieval. Current legacy MemoryService has no semantic MemoryProvider, so that row is not directly reconstructed into Runtime P8 as a semantic `MemoryEvent`; Runtime receives an unavailable semantic Memory outcome in this mode. If generated or lineage-bearing Memory is exposed to P8 in the future, model-owned `originRole: user` alone still cannot authenticate it or make it verified user evidence.

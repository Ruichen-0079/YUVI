# A10.1b — Committed Journal receipt ancestry validation

**Status:** IMPLEMENTED REALITY. Implementation base: `61c7d3d2b4d61adc676c2ac3b0c9f186d41f861e`.

## Source audit and change

Before this leaf, conversational HTTP/SSE/WebSocket routes committed an A8.2b Journal `RECEIPT`, then constructed or forwarded the Runtime user event. The committed event identity was logged but not carried on the event. Finalized speech was different: A8.2c already held the exact committed Journal reference in Runtime's pending speech handoff state, but `commitSpeechTurn()` omitted it from the resulting `user.voice.transcript` event. Runtime then persisted user conversation rows with Runtime/conversation identifiers and no typed Journal ancestry.

The new first-class `sourceJournalRef: JournalEventRef | null` conversation field is distinct from Runtime event/trace IDs, conversation message ID, `sourceUserEventId`, speech observation/capture IDs, Memory event IDs and backend IDs. In particular, `sourceUserEventId` retains its existing Runtime/source-user-event meaning. The host derives `JournalEventRef` only from the committed envelope's namespace and event ID; request input cannot establish that authority. The websocket route replaces any caller-supplied ref with the newly committed host ref. HTTP schemas do not expose the field.

`/message`, `/v1/messages`, `/v1/messages/stream` and `/ws` attach the reference to their Runtime user-turn carrier after the existing receipt commits. Speech reuses its pending committed reference through `commitSpeechTurn()` and does not append a second receipt. Runtime persists ancestry only on the user conversation message; assistant messages keep it null. The receipt's principal, Person binding and audience remain unresolved/unknown as before. No payload catalog or selector is copied to the conversation row; later consumers must resolve the committed Journal parent and validate its retained/selectable payload state. The conversation repository rejects malformed refs, assistant ancestry and idempotent message-ID retries with a different ancestry.

Migration `014_conversation_journal_ancestry_v1.sql` adds nullable JSONB `source_journal_ref`. Existing rows read as null; migration is idempotent. In-memory and PostgreSQL repositories share the same typed field and round-trip behavior. If conversation persistence fails after Journal commit, the receipt remains committed; no text lookup or compensating deletion is attempted.

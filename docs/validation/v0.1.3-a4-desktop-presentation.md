# v0.1.3 A4 — Desktop presentation status validation

## Scope and starting point

A4 exposes a read-only view of what the desktop surfaces and Live2D renderer are actually presenting. It uses the existing surface and renderer owners; it adds no persistent state and no global presentation store.

## Authoritative ownership traced

| Status | Authority | Projection input |
| --- | --- | --- |
| Companion visibility | `DesktopSurfaceManager` and the native Companion window; its presentation query reads actual window visibility | Existing `getCompanionPresentationState` Tauri query and `desktop-surface.changed` refresh path |
| Live2D lifecycle/readiness | `LumiCanvas` → current `LumiController` → `Live2DAdapter.load`; the controller reports `ready` only after renderer setup succeeds and reports `failed` on its current load failure path | Current controller lifecycle callback and its existing generation/disposal fencing |
| Active Live2D model identity | The current `LumiController`, paired with the exact model identity passed for its load request; exposed only when that controller is ready | `getActiveModelIdentity()` gated on ready, then projected by `deriveCompanionRendererPresentation` |
| Subtitle visibility | `DesktopSurfaceManager` and the native subtitle window | Existing subtitle presentation query |
| Subtitle lock | `DesktopSurfaceManager` subtitle window state and its existing lock command | The same subtitle presentation query; it is independent of visibility |

The projection seam is `apps/web/src/companion-presentation-projection.ts`, extending its existing typed renderer status and BroadcastChannel request/state path. Companion and subtitle window status continue to come from their existing Tauri surface queries and runtime refresh events. No new backend command, global aggregate store, or second Live2D lifecycle was added.

## Exposed states and behavior

- Companion surface: `visible` or `hidden`, based on the window owner query. A failed/unavailable query remains unknown in the appearance view instead of defaulting to hidden.
- Live2D renderer: `no_model`, `loading`, `ready`, `failed`, or `unavailable` when current renderer truth cannot be proved. Only `ready` contains `activeModel: { id, name }`; loading and failure may identify a `requestedModel`, which is not labeled active.
- Subtitle surface: visibility `visible`/`hidden` and lock `locked`/`unlocked`, read independently from the existing owner. Unknown query results are not defaulted to hidden or unlocked.

Configuration and model discovery can supply a load request, but cannot establish renderer readiness. `ready` requires the current controller's successful renderer lifecycle and its active model identity. Errors are not included in the projection. A selected or configured model without renderer success stays non-ready.

### Replacement and discovery invariants

- The existing controller generation IDs, disposal behavior, and stale-result fencing remain the lifecycle authority. A4 reuses them.
- A stale old success or failure cannot replace the current controller's status. The current request is paired with its model identity; status publication comes from that request's controller lifecycle callback.
- A transient model-list polling/discovery failure does not report renderer failure and does not clear a still-current loaded model. A missing/unavailable discovery response does not override an existing truthful renderer state.
- A genuine current load/renderer failure is reported as `failed`; a disposed controller or missing proof is `unavailable`, not a fabricated failure.

### Evidence isolation

The renderer projection takes only the renderer lifecycle and the current/requested model identity from the Live2D presentation path. It does not read Character, Memory, conversation history, later context, cognition execution evidence, or persisted selected-model settings to report runtime readiness or active identity. Settings and discovery data may initiate a renderer request, but readiness comes only from the actual current controller. Companion visibility and subtitle visibility/lock are read from the window owner.

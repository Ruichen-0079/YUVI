## Implemented admission and ordering

`apps/server/src/runtime-control-receipt-admission.ts` adds a narrow host-owned facade. Its strict input admits only P8 correction action/target kind (and a fixed authored-invariant enum when applicable) or read-text authorization. It receives no request body, Runtime, P8 store, path or correction content. It builds a fresh host-owned `RECEIPT/CONTROL` with a minimal retained TEXT summary and calls `JournalRepository.appendWithHostAuthority`. No `sourceDedup` is sent.

### P8 correction

The route parses the canonical P8 record, then calls Runtime's read-only `preflightP8Correction`. `RuntimeOrchestrator.inspectP8Correction` uses `createP8CorrectionRecord` / `serializeP8CorrectionRecord` for canonical equality and shares the existing `reconstructP8MainProfile` target/lineage validation. The stores provide read-only exact-scope reads plus a global correction-reference lookup so changed content under a reference already used in another scope is rejected before Journal admission.

- New valid reference: preflight validates current reconstruction and returns READY without changing store state.
- Same canonical record under an existing reference: may receive another CONTROL receipt; final append reloads/revalidates and returns `ALREADY_STORED`.
- Changed record under an existing reference, invalid target or invalid lineage: rejected before Journal admission, with no receipt.
- After receipt commit, final append reloads and validates again. P8 is not reserved by preflight. A concurrent state change can yield a bounded `CONFLICT`/`ERROR`; the receipt remains, the competing correction is not overwritten, and no OUTCOME is appended.

Correction references are stable P8 domain identity, not a trusted transport redelivery key. Equal canonical requests therefore create distinct Journal receipts. The receipt retains only operation, action, target kind and, where needed, a fixed invariant-target enum. It withholds correction reference, replacement meaning, provenance reference/time, superseded evidence references, arbitrary target keys and the complete record.

### Read-text authorization

Before Journal admission, the route now matches Runtime's accepted input contract, including a non-whitespace session ID, exact path trimming, absolute path and the existing 4096-character bound. Only after the CONTROL receipt commits does the route call `Runtime.authorizeReadText` with the original session/path values.

The retained receipt contains only `{"operation":"capability.read-text.authorize"}`. It has no path, basename, path hash or file content; receipt creation performs no filesystem read. The actual grant remains the existing process-local Runtime map, including same-session overwrite and one-shot consumption. A receipt survives repository reopen, but a new Runtime does not restore or replay the grant.

## Failure and authority contract

- Journal unavailable or persistence failure returns bounded 503 and prevents P8 append/read-text grant mutation.
- Malformed or known-invalid/conflicting P8 input and invalid read-text input are rejected before receipt admission.
- A post-receipt P8 race is not rolled back across stores. The committed receipt remains even if final append returns conflict/error.
- A receipt means only “YUVI accepted this locally authorized Runtime control command for processing.” It does not establish P8 persistence/current truth, later file use, or grant survival.
- No OUTCOME, DERIVATION, A9 dispatch, A10 lineage, replay, retry or reconciliation was added. `POST /v1/proactive/consent` and voice controls were not changed.

## 1. V1 的能力，按真实状态分四类

| 类别                         | 能力                                                                                                                                                                                       | V2 怎么对待                                                    |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| **实际可用**（main）         | 网页 / 桌面文字对话（流式）；人设；跨会话记忆（Mem0 / 规则抽取，有已知损失）；定时主动开口与同意设置；本地语音输入 + 声纹识别；语音输出；Live2D 形象与模型导入；Linux 桌面安装；崩溃不重放 | **必须恢复**，按 V2 架构重做，体验不低于 V1                    |
| **分支中实现、真实在用**     | QQ / SnowLuma 接入与 Alice 人设（Plunge 分支，未合并，但 Alice 实际在 QQ 中运行）；带作者的线性上下文                                                                                      | **必须恢复**，这是 Alice 现在的生活                            |
| **已实现但未充分验证或接入** | 按需截屏看图（视觉模型验收跳过）；GLM 推理升级；Profile 物化（无读方）；Dream 整合（从未触发）；效果账本的全覆盖；R4/R5 纠正与记忆权威、发行候选与冷恢复（未合并）                         | 只恢复其中的**用户能力**：看图、纠正生效、备份恢复。其余不复刻 |
| **只在文档或规划中**         | 后训练角色模型、Harness 适配器、前瞻连续性、Life Layer、测量整合、E1–E8 实验设施、Windows 发行                                                                                             | 不复刻                                                         |

**V2 真正新增的研究能力：**

- 不预设语义的潜在组织（心境）；
- 重建式记忆（档案与记忆分开）；
- 它自己的世界与自由时间；
- 私人场景；
- 换模型后的连续性。

**说明：**

- **时间是估计。** 前提是 Sol 每个 P 一次通过；返工按实际情况顺延，不压缩验收。
- **研究不阻塞产品。** 潜在组织的离线实验（蓝图 X12、X13）可以从 C2 起作为不阻塞的旁路开始：它只读 `v2-dev` 的副本，不改产品代码。是否开始，由你决定。
- **研究宗旨在 C1–C5 中的落实方式是“不堵死”，不需要额外工作量：**
  - 档案从第一天起就有 `inner` / `control` 类别和 `branch` 字段；
  - 程序不加任何情绪、意图、重要性标注；
  - `recall` 返回它自己的回忆，不是档案原文；
  - 事件预留 `latent_ref`。
- **相对蓝图的简化：** Alice 切换不再以 X1–X3 实验为门槛，改为“功能验收 + 你使用 1 周 + 恢复演练 + 你批准”。X 系列实验在 C6 起作为研究进行。
- **测试、部署与数据保护**随每个 P 一起交付，不单列周期，也不作为延期理由。

## 3. 每个 P 的固定格式

- **P 文件：** 目标、范围（做 / 不做）、对外接口与约束、验收标准、交付约定，一页到两页。
- **验收标准在交给 Sol 前确定。** Sol 可以因真实的技术障碍提出修改，并说明原因：
  - 不涉及范围的修改，由 Claude 决定；
  - 涉及范围或架构的修改，交给你决定。
- **Claude 的验收：**
  - 独立运行 P 文件中的检查（用自己写的脚本与假模型服务）；
  - 审阅代码是否违反蓝图附录 C.1 的不变量；
  - 结果记录在 PR 评论里：通过 / 不通过，以及不通过时对应的检查项。
- **不在验收中提出新要求。** 发现的范围外问题，记为下一个 P 的候选。

# A10.1 — Grounded Memory admission, lineage and profile materialization roadmap

> **Status:** CURRENT A10.1 LEAF EXECUTION ROADMAP — aggregate A10.1 remains **PLANNED / INCOMPLETE**.
>
> This file freezes the source-audited implementation sequence after aggregate A8.2 closure. It exists to prevent A10.1 from collapsing back into one oversized implementation atom or being reduced to only the legacy LLM extractor defect. Source reality, `09-v0.1.3-platform-completion.md`, `implementation-baseline.md`, `memory-and-lineage.md`, and validation records remain authoritative when they disagree with stale prose.

## Why A10.1 is split

A8.2 established durable admission for the documented semantic/control receipt family. A10.1 answers the next question: once a fact, statement, derived record, or profile projection is written or materialized, what committed evidence actually supports it?

The source audit still uses six top-level leaves so existing release sequencing remains stable. A10.1f is now a bounded sub-sequence because the current Mem0 generation already exposes a User Profiles capability and profile materialization touches the same Memory/provider boundary that A10.1 is opening anyway.

```text
A10.1a  Fail closed on legacy LLM evidence
   ↓
A10.1b  Carry committed Journal receipt ancestry
   ↓
A10.1c  Ground new legacy Memory writes
   ↓
A10.1d  Ground finalized Mem0 ingestion / modernization boundary
   ↓
A10.1e  Ground dream derivations
   ↓
A10.1f1 ProfileProvider ABI + local grounded materializer
   ↓
A10.1f2 People.Model bridge + dirty/regeneration semantics
   ↓
A10.1f3 Aggregate dual-backend/profile lineage closure
```

The order is deliberate. Do not skip directly from A10.1a to backend lineage. A10.1b establishes the ancestry seam required by later consumers. A10.1f must not make profile generation a second evidence authority: it consumes grounded Memory and exposes a derived projection only.

The exact c/d/e file boundaries may be refined after A10.1b if source ownership reveals a cleaner shared grounded-consumer contract. Preserve the invariants and dependency order rather than an artificial file split.

## Shared A10.1 invariants

- Generated/model content must never become user evidence merely because the model labels it `user`, assigns high confidence, or supplies user-like metadata.
- Host/consumer authority owns Journal parent IDs, eligible selectors, source scope, principal/binding/audience states, and authoritative timing.
- Model output may propose semantic content; it must not assign authoritative lineage.
- New factual evidence-backed writes require eligible committed evidence. If grounding cannot be proved, fail closed.
- Deliberately unretained payloads remain explicitly unavailable; do not fabricate exact selectors.
- Runtime IDs, conversation IDs, Memory UUIDs, finalized child IDs, episode IDs, profile revisions, provider/backend IDs, and Journal event IDs are distinct identities unless an explicit typed mapping says otherwise.
- Assistant output is generated evidence, not silent user evidence.
- Hearsay remains attributed hearsay; committed lineage proves what was said/reported, not that the reported world proposition is true.
- Old rows and episodes may be `LEGACY_INCOMPLETE`; never invent historical receipts, audiences, Person bindings, or clocks.
- Preserve one active Memory backend and existing finalized/dream keyed delivery, lease, idempotency, and reconciliation machinery. A10.1 adds ancestry and a derived profile materializer; it does not create another Memory authority or delivery engine.
- Semantic Memory/Profile task identity is independent of execution model tier, provider, and backend. `Local`, `Chat`, `Cognition`, provider names, model names, and backend IDs are execution/provenance facts only; none grants evidence, Person, or Memory authority.
- Changing which model executes extraction, dream derivation, or profile synthesis must not change the host-owned grounding contract. A stronger model is not a stronger authority.
- A10.1 must not encode a specific model tier as the semantic identity of Memory extraction, finalized ingestion, dream derivation, or profile synthesis. Model-selection and escalation policy remain outside this atom.
- A profile is derived and disposable. It can be invalidated and regenerated from eligible Memory/evidence; deleting it must not delete the underlying evidence or Person identity.
- Profile output cannot silently promote itself into `People.Facts`, Memory evidence, Person identity, relationship authority, or the source set for its next regeneration.
- Corrections/amendments invalidate affected profile descendants; regeneration must converge from the current eligible Memory set rather than accumulate unbounded patches.
- A9 effect accounting is separate.
- Authored/controller Person-field writes, controller→Person authentication, voice-binding, and P8 correction issuer/binding lineage remain A10.2.
- Context-use manifests remain A10.3.

## Model-execution neutrality

A10.1 defines grounded Memory/Profile semantics, not an inference-budget router. Future execution policy may choose a local model, Chat-class model, Cognition-class model, deterministic code, or another approved implementation for a semantic task without changing that task's authority or lineage rules.

Conceptually:

```text
semantic task / derivation kind
   ↓
future execution policy
   ↓
concrete implementation / provider / model
   ↓
host validation of committed lineage
   ↓
Memory admission / derived profile materialization
```

The semantic task and execution choice are different identities. Do not introduce contracts equivalent to `MemoryExtractor = Cognition`, `Dream = Cognition`, `Profile = Chat`, or `model tier = authority`. The existing `LlmMemoryExtractor` name is a legacy implementation identifier and must not become the target semantic abstraction.

Execution provenance may be recorded for audit and reconstruction when available, but it is descriptive. It cannot supply Journal parents, selectors, principal/binding/audience state, authoritative time, Person identity, or admission permission.

No Local → Chat → Cognition escalation policy is implemented by A10.1. This roadmap only preserves the seam needed for such policy to be introduced later without rewriting Memory/Profile semantics.

## A10.1a — Fail closed on legacy LLM evidence

**Status:** IMPLEMENTED REALITY. See [A10.1a validation](../validation/v0.1.3-a10.1a-llm-memory-grounding.md).

**Goal.** Immediately close the reproduced legacy LLM attribution vulnerability without pretending committed selector grounding already exists.

Current audited defect:

- optional legacy `LlmMemoryExtractor` forces accepted candidates to `originRole: "user"`;
- model `sourceTraceId` can override the host source trace;
- model observation/event/validity times can override host timing;
- provenance enrichment trusts model-declared user-like provenance and can attach unrelated user text as `evidenceText`;
- later admission can store the generated proposition as durable Memory.

Current LLM-selected legacy extraction therefore fails closed through the existing rule-based path and reports `unsupported-grounding`; it does not invoke the reasoning provider. Shared, server-boot and reload configuration parsing reject unknown extractor values.

**Non-goals.** No Journal ancestry plumbing, no Memory lineage schema, no finalized/dream/profile changes, no Local/Chat/Cognition router, no A10.2/A10.3/A9 work.

## A10.1b — Carry committed Journal receipt ancestry

**Status:** IMPLEMENTED REALITY. See [A10.1b validation](../validation/v0.1.3-a10.1b-journal-ancestry.md).

**Goal.** Preserve the exact committed A8.2 receipt reference across Runtime/conversation persistence so downstream Memory consumers can identify the actual source event.

Implemented boundary:

- A8.2b HTTP, SSE and WebSocket routes attach the exact host-derived `JournalEventRef` from the just-committed receipt to the Runtime user-turn carrier;
- finalized speech carries the existing pending receipt ref through `commitSpeechTurn()` into the voice transcript event, with no second append;
- the conversation repository persists this ref in a nullable `source_journal_ref` field; old rows remain null and assistant rows do not inherit user ancestry.

Required properties:

- persist the existing committed Journal reference rather than minting another one;
- keep Journal, Runtime event, conversation message, source user-event, observation, Memory and backend identities distinct;
- preserve the speech handoff's one original receipt and existing stale-epoch fences;
- carry unresolved principal/Person/audience states unchanged;
- do not duplicate payload catalogs or fabricate selectors on conversation rows; downstream consumers resolve the committed parent and validate its selector/retention state;
- do not infer identity from local access, caller hints, `subjectUserId`, acoustic matches, or display names.

No backend admission-policy rewrite, selector-resolution service, or Memory grounding decision belongs here. A committed receipt remains even if later conversation persistence fails; old rows are never matched to receipts by text.

## A10.1c — Ground new legacy Memory writes

**Status:** IMPLEMENTED REALITY. See [A10.1c validation](../validation/v0.1.3-a10.1c-grounded-legacy-memory.md).

**Goal.** Require host-validated committed Journal evidence for new evidence-backed legacy Memory writes while leaving Mem0 finalized ingestion and dream lineage to later leaves.

Implemented boundary:

- `MemoryService` requires a separate Runtime-owned Journal reference and source text, resolves the exact committed RECEIPT, and validates a retained/selectable TEXT selector against the exact source text before candidate admission;
- the host constructs versioned `MemoryLineageV1` with the exact parent/selector, receipt origin, recorded time and unresolved principal/Person/audience snapshots; candidate metadata cannot set lineage authority;
- new grounded legacy rows persist atomically with a stable consumer key and payload digest; exact replay returns the original row and a conflicting replay fails closed;
- explicit remember and corrections are grounded by the current correction/utterance receipt; old rows remain null-lineage `LEGACY_INCOMPLETE` and are never backfilled by text or trace matching;
- manual/synthetic Memory writes must be explicitly marked `NON_EVIDENCE`; dashboard candidate review retains its host grounding separately and cannot patch content into new evidence.

Finalized Mem0 ingestion, dream ancestry and Profile materialization remain in A10.1d–f. Model execution tier is independent of grounded Memory semantics; this leaf adds no tier router or escalation policy.

## A10.1d — Ground finalized Mem0 ingestion and modernization boundary

**Status:** PLANNED ENGINEERING.

**Goal.** Freeze validated committed ancestry into the existing finalized-turn child payload, carry it through the Mem0 boundary, and perform the Mem0 dependency migration needed by the current local stack without changing semantic authority.

Reuse existing finalized-ingestion machinery:

- finalized turn identity;
- stable child event ID/key;
- payload digest;
- backend idempotency key;
- lease/claim lifecycle;
- dispatch-start marker;
- reconciliation.

Mem0 rules:

- `infer: false` remains the finalized evidence-admission boundary unless a later explicit authority decision replaces it;
- backend UUID is not a Journal event ID;
- finalized child ID is not a Journal event ID;
- Journal parent, child identity, and backend identity remain distinct;
- lineage encoding must round-trip through the actual Mem0 metadata sanitizer without silently dropping/truncating selectors;
- Journal read unavailability for new grounded work must not produce fabricated ancestry;
- local PostgreSQL/pgvector ownership, private embedding behavior, health/lifecycle, packaging, idempotent delivery and reconciliation must be regression-tested across the chosen Mem0 upgrade;
- an upstream feature is not adopted merely because the new package exposes it; YUVI contracts remain authoritative.

As of the 2026-09-23 upstream release, Mem0 Python `2.2.0` / TypeScript `3.3.0` adds User Profiles to the hosted `MemoryClient` APIs. That capability is a relevant compatibility target for A10.1f, but it is not evidence that OSS `Memory.from_config(...)` now provides a local profile service. A10.1d must record the exact local/hosted capability split for the version actually adopted.

Do not add another executor or retry protocol.

## A10.1e — Ground dream derivations

**Status:** PLANNED ENGINEERING.

**Goal.** Preserve committed source ancestry through episode construction and dream derivation.

Current episode compression keeps statement text/conversation IDs but not exact per-statement Journal ancestry. Capture source-message → committed receipt/selector mapping before compression.

```text
committed receipt
   ↓
grounded source statement
   ↓
episode
   ↓
dream derivation
   ↓
Memory child
```

Dream output is `DERIVED`, never a fresh original user receipt. Episode IDs are not original receipts. Old episodes lacking source mapping remain incomplete; do not backfill them by matching text.

Dream is a semantic derivation path, not a Cognition-owned authority. The concrete executor may change in future — including local, Chat-class, Cognition-class, or deterministic implementations — without changing `DERIVED` origin, committed-parent requirements, selectors, or Memory admission semantics. If model/provider identity is retained, record it only as execution provenance.

Preserve the current keyed dream delivery/reconciliation path.

## A10.1f — Profile materialization and aggregate closure

A10.1f is intentionally split into three bounded sub-leaves. Implement and validate them in order.

### A10.1f1 — ProfileProvider ABI + local grounded materializer

**Status:** PLANNED ENGINEERING.

**Goal.** Reuse the Mem0 modernization window to add a YUVI-owned profile provider boundary and a local profile materializer over the newly grounded Memory set.

The provider contract should expose only the semantic operations actually needed, conceptually:

```text
ProfileProvider
  getProfile(person/profile subject)
  generate/regenerate(profile subject, source revision)
  getGenerationStatus(job/revision)
  report capabilities/version
```

The concrete API may be smaller if repository seams permit. The important boundary is ownership, not method names.

Required behavior:

- local/private operation is the default capability; People/Profile must not require Mem0 Platform;
- profile shape is controlled by a versioned YUVI JSON Schema or equivalent typed contract;
- each materialized snapshot records profile revision, producer/provider version, source-set digest/revision, generation status and inherited scope information sufficient for later validation/disclosure;
- semantic entries must be reconstructible from eligible lineage-bound Memory claims or explicitly marked partial/unknown/unavailable;
- conflicts remain conflicts rather than being silently resolved by a model;
- a model may structure/summarize eligible evidence, but cannot invent evidence IDs, Person bindings, times, visibility, or authoritative facts;
- raw profile prose is never fed back as original evidence on the next regeneration.

Mem0 compatibility:

- the hosted User Profiles API may be implemented as an optional adapter if explicitly configured and if its returned projection can be validated against YUVI's contract;
- because the current upstream profile API is hosted-client functionality, YUVI must also have a local materializer with equivalent high-level lifecycle semantics rather than moving Memory/People authority to the cloud;
- hosted asynchronous jobs must preserve request/job identity and explicit pending/failed/unknown states; where upstream idempotency keys exist, use and test them without claiming stronger exactly-once semantics.

### A10.1f2 — People.Model bridge + dirty/regeneration semantics

**Status:** PLANNED ENGINEERING.

**Goal.** Connect the derived profile snapshot to `People.Model` while preserving the distinction between facts, model, and relationship adaptation.

Canonical ownership:

```text
People
├── Facts
│   └── governed Person fields + grounded Memory/evidence
├── Model
│   └── derived ProfileProvider snapshot
└── Relationship adaptation
    └── separate later measured/relationship mechanisms
```

Required behavior:

- a committed Memory correction/amendment or eligible binding/source revision marks dependent profile materialization dirty;
- dirty updates are coalesced and run as background work rather than synchronously regenerating on every message;
- regeneration reads the current eligible Memory set and produces a new revision; it does not append an endless profile patch chain as semantic truth;
- previous snapshots become stale/superseded according to explicit policy and never outrank corrected source evidence;
- `People.Model` may read the derived snapshot, but `People.Facts` cannot be populated merely because a profile field exists;
- relationship trust/disposition, commitments, identity authentication and authored Person fields are not profile primitives.

Execution ownership remains Cognition/background infrastructure semantically even if a local or Chat-class model executes the synthesis. The executor tier is policy, not architecture.

Required aggregate coverage includes:

- unrelated evidence text;
- assistant-only paraphrase;

- local profile generation;
- optional hosted-profile capability detection/adapter behavior if configured;
- profile generation failure/pending/stale states;
- profile correction invalidation and replay convergence;
- profile fields unable to promote themselves into Facts/evidence;
- producer/provider/model metadata never substituting for host-owned lineage or admission authority;
- Memory/Profile semantics remaining stable when execution provenance changes;

## Canonical lineage direction

The source audit recommends a small host-constructed versioned lineage representation for new evidence-backed Memory consumers, conceptually:

```text
MemoryLineageV1

state:
  GROUNDED
  | PAYLOAD_UNAVAILABLE
  | LEGACY_INCOMPLETE

parents:
  JournalEventRef[]

selectors:
  validated SourceSelector[] associated with their parent

sourceAvailability:
  retained/selectable
  | explicitly unavailable with reason

child:
  immutable finalized/dream consumer identity

derivation:
  semantic task / derivation kind
  producer component/version
  policy version
  optional execution provenance:
    implementation/provider/model/version

origin:
  USER_ASSERTION
  | EXTERNAL_OBSERVATION
  | ASSISTANT_GENERATED
  | DERIVED

scope:
  Memory storage scope
  plus principal / Person binding / audience state
  exactly as actually known
```

Profile snapshots reference the eligible grounded Memory/source revision they were generated from; they do not pretend to be additional original Journal receipts.

This is an implementation direction, not a model-writable authority object. The owning consumer validates it. Execution provenance is descriptive and must not affect lineage authority or origin classification. `LEGACY_INCOMPLETE` is compatibility-read state only and is never a valid escape hatch for a new evidence-backed write or a strong profile claim.

## Semantic examples

`"My friend says the restaurant is closed."` grounds the user's report that the friend made the assertion; it does not verify that the restaurant is closed.

Assistant: `"You seem to prefer astronomy."` followed by user `"Okay."` does not create a new user preference claim.

User: `"Yes, remember that I like astronomy."` creates a current grounded user assertion/request, while preserving whatever unresolved identity state its receipt actually contains.

A user correction is grounded by the new correction receipt and linked to the prior Memory/claim. The old claim is not rewritten into a fabricated original receipt. Any dependent profile snapshot becomes dirty/superseded and is regenerated from the corrected eligible source set.

## Explicit exclusions

A10.1 does not implement:

- controller → Person authentication;
- voice-binding lineage;
- authored/controller Person-field authority and its control lineage;
- P8 correction issuer/binding lineage;
- relationship trust/disposition learning;
- commitment/prospective state;
- People product UI;
- context-use manifests;
- Local/Chat/Cognition task routing, model-tier escalation, or inference-budget policy;
- cross-backend privacy erasure;
- A9 INTENT / ATTEMPT / OUTCOME or effect outbox/retry/reconciliation.

Those remain A10.2, A10.3, v0.1.4 People product work, A9, post-v0.1.3 execution-policy/research work, or later work. Derived profile synthesis/materialization itself is no longer deferred to A10.2 or v0.1.4.

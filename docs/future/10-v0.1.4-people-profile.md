# v0.1.4 — People & Profile

> **Status:** PLANNED ENGINEERING
>
> **Entry condition:** v0.1.3 Durable Causal History Foundation is closed through A12.2 with the six release invariants proven on the synthetic surface and the pinned QQ/Snowluma probe.
>
> **Purpose:** make People a first-class cross-surface YUVI capability and expose an evidence-linked, regenerable profile for each Person without turning QQ, Mem0, an LLM, or the profile itself into identity/relationship authority.

This is a **core product release**, not a plugin release. QQ is the first high-value multi-person surface, but QQ owns only transport normalization. Profile generation and use belong to YUVI core domain ownership.

---

## 1. Release outcome

At closure, YUVI can answer four different questions without conflating them:

1. **Who is this principal?** — governed principal → Person binding.
2. **What evidence has YUVI retained about this Person?** — journal/Memory with provenance and audience.
3. **What profile can be derived from that eligible evidence right now?** — disposable/versioned profile projection.
4. **What parts of that profile may be exposed in this current context?** — A4 disclosure/context policy.

Conceptually:

```text
surface principal
      ↓ explicit/governed binding
    Person
      ↓
committed retained evidence
      ↓
lineage-bound Memory claims
      ↓
Person Profile projection
      ↓
People UI / A4 context projection
```

A profile is never a replacement for Person identity, raw evidence, relationship measurements, commitments, or charter policy.

---

## 2. Release invariants

### PP-I1 — One Person authority

The current governed Person owner remains the authority for Person identity. No profile provider, Mem0 feature, QQ adapter, model output or Memory row can create an authenticated binding by itself.

### PP-I2 — Profile is derived and disposable

A profile can be deleted and regenerated from eligible retained evidence plus explicit authored/controller data. Losing the profile store must not erase original evidence or Person identity.

### PP-I3 — Every semantic profile claim is grounded

Every generated/aggregated profile field or section must reference eligible source claim/event IDs or be explicitly marked unavailable/unknown. A model may summarize grounded claims; it may not create unsupported profile facts.

### PP-I4 — Audience/disclosure never widens

Private evidence cannot become group-visible because it was summarized into a profile. Profile generation records source scope, and A4 applies current disclosure policy before any profile projection reaches Cognition/Character.

### PP-I5 — Corrections invalidate descendants

A source amendment, binding correction or eligible Memory correction invalidates dependent profile snapshots and context caches. Stale profile output is withheld or visibly stale until regeneration.

### PP-I6 — Backend neutrality

The People/Profile product works without requiring Mem0 Platform. Mem0 is an optional implementation asset behind YUVI-owned contracts. No upstream package/API becomes the semantic owner of Person/profile behavior.

---

## 3. Current Mem0 reality that must be preserved until audited

At the current audited repository state:

- `services/memory-mem0/requirements.txt` pins `mem0ai==0.1.107`;
- the local sidecar uses `Memory.from_config(...)`, not the hosted `MemoryClient` as its core path;
- YUVI has a private Ollama embedder compatibility patch whose current strict path is tied to the pinned Mem0 version for private `yuvi-*` embedding tags;
- finalized YUVI → Mem0 delivery uses YUVI-owned idempotency/reconciliation semantics and `infer=false` rather than delegating semantic admission to Mem0;
- Mem0 remains a Memory backend/index, not canonical journal or Person authority.

Upstream Mem0 has evolved substantially since that pin. Current upstream capabilities, OSS migration semantics, hosted/Platform-only features, profile APIs and package compatibility **must be re-verified at PF2 execution time**. This roadmap intentionally does not assume that a current upstream User Profile feature exists in OSS, is safe for local use, or should replace YUVI's profile contract.

# PF1 — People/Profile ownership, schema and provider contract

**Status:** PLANNED ENGINEERING.

**Goal.** Freeze the semantic boundary for Person identity, authored Person data, derived profile data and profile providers before implementing any profile generator.

**Why this atom exists.** Without an explicit boundary, QQ identity, current product-store Person fields, Memory evidence, P8 projections and a new Mem0 profile feature can easily become competing authorities.

**Preconditions.** v0.1.3 closed; read `identity-and-provenance.md`, `memory-and-lineage.md`, `p8-ownership.md`, A10.2/A10.3 validation and current People/product-store implementation.

**Existing authority to preserve.** Governed Person/product-store ownership; principal→Person binding authority; P8 authored identity/correction ownership; A4 canonical context; Memory as evidence/index only.

**Exact scope.** Define a versioned YUVI-owned profile contract. Naming may follow existing source conventions, but the semantic shape must distinguish at least:

- authoritative Person reference / revision;
- profile revision and producer/provider version;
- source-set digest / committed source references;
- generation time and retention state;
- section/field status (`KNOWN`, `PARTIAL`, `CONFLICTING`, `UNKNOWN`, `UNAVAILABLE`, or equivalent);
- evidence references/selectors for every semantic field/section;
- visibility/audience constraints inherited from sources;
- optional rendered narrative summary separated from structured grounded entries.

Candidate semantic sections may include background facts, explicit preferences, communication preferences, interests/common topics, routines/workflows and other ordinary user-profile knowledge. The final schema must be driven by existing claim/evidence types and real product needs, not by a desire to fill fields.

Define a narrow provider/projector interface owned by YUVI, conceptually similar to:

```text
PersonProfileProvider
  get current snapshot
  generate/regenerate from an authorized evidence set
  report provider capability/status
```

The exact API should fit repository seams; do not force this literal TypeScript shape if a smaller existing abstraction is sufficient.

**Explicit non-goals.** No profile generation; no Mem0 upgrade; no relationship trust/scalar state; no commitment state; no automatic Person binding; no new Person database; no QQ-owned profile store; no UI.

**Expected code/docs to inspect.** Current product-store/People services and routes; A10.2 identity/control paths; Memory claim/provenance types; P8 ownership map; A4 context assembly; `services/memory-mem0` provider boundary.

**Required invariants.** PP-I1–PP-I6. Authored Person fields and derived profile fields cannot silently share writer authority. A provider cannot return authoritative Person bindings.

**Failure semantics.** An ungrounded field or unknown source scope cannot be promoted into a normal known profile value. Schema/version mismatch fails visibly rather than coercing old data.

**Required tests.** Type/schema validation; attempted profile overwrite of Person identity; missing evidence references; conflicting evidence; private/group audience conflict; unknown provider capability.

**Migration/compatibility concerns.** Current Person/product-store data remains authoritative. P8 remains unchanged. Existing Memory retrieval behavior is not rewritten.

**Exit criteria.** One reviewed profile schema/contract exists in code/docs with tests proving authority separation; no production generator is enabled.

**Validation record.** `docs/validation/v0.1.4-pf1-profile-contract.md`.

**Downstream.** PF2 and PF3.

**Must NOT be implemented early.** Mem0 SDK upgrade, profile UI, profile prompt injection or automatic QQ account linking.

# PF2 — Mem0 capability, upgrade and profile-path audit

**Status:** PLANNED ENGINEERING / DECISION GATE.

**Goal.** Determine the safest Mem0 path for v0.1.4 using the actual current upstream state rather than package-version enthusiasm.

**Why this atom exists.** YUVI currently depends on a pinned 0.1.107 sidecar plus a private embedder patch and custom idempotent delivery. New upstream extraction/retrieval/profile features may be valuable, but an upgrade can silently change Memory semantics or break local packaging.

**Preconditions.** PF1; current v0.1.3 Memory lineage/reconciliation tests are green.

**Existing authority to preserve.** YUVI MemoryProvider contract, YUVI-owned idempotency/reconciliation, `infer=false` finalized writes, local PostgreSQL/pgvector ownership, profile contract from PF1.

**Exact scope.** Perform a read-only/upstream compatibility audit and produce one explicit decision record. At minimum compare:

1. current YUVI baseline (`mem0ai==0.1.107`);
2. current latest supported Mem0 OSS/self-hosted path;
3. current Mem0 hosted/Platform client capabilities relevant to generated user profiles, if they exist;
4. whether profile generation is available in OSS, Platform-only, both, or neither at execution time;
5. extraction changes (including ADD-only or other current algorithm changes);
6. retrieval changes (semantic/BM25/entity-aware/hybrid/reranking as applicable);
7. pgvector schema/API compatibility;
8. custom/private Ollama embedder compatibility and whether the YUVI patch is still required;
9. YUVI's direct idempotent backend write/reconcile implementation compatibility;
10. metadata, filtering, deletion/history behavior;
11. Python/runtime/package/packaging size changes for Linux and current desktop bundle;
12. cloud disclosure/privacy implications if a hosted profile service is considered.

The decision must choose and justify exactly one default path for v0.1.4:

- `KEEP_PINNED_MEM0` — keep 0.1.107 for Memory and use the YUVI-native profile implementation;
- `UPGRADE_OSS_MEM0` — upgrade local OSS only after compatibility tests prove the YUVI contracts can be preserved;
- `ADD_OPTIONAL_PLATFORM_PROFILE_PROVIDER` — keep local Memory authority while adding an explicitly configured hosted profile provider behind PF1's contract;
- another narrowly specified path supported by source/upstream evidence.

A cloud/Platform path must never become mandatory merely to make People/Profile work.

**Explicit non-goals.** No production dependency change; no package upgrade; no profile implementation; no migration of existing memories; no assumption that upstream marketing language matches YUVI semantics.

**Expected code/docs to inspect.** `services/memory-mem0/requirements.txt`, sidecar `memory.py`, config/embedder patch, provider/backend adapters, desktop packaging scripts/tests, current upstream release/migration docs and APIs.

**Required invariants.** PP-I6; v0.1.3 Memory lineage and crash semantics cannot regress. Hosted data disclosure requires explicit configuration and must be documented.

**Failure semantics.** Unclear upstream guarantees count as unsupported. If private embedder/idempotent paths cannot be proven compatible, `UPGRADE_OSS_MEM0` is rejected for this release.

**Required tests.** This atom is primarily an audit, but any compatibility spike must be isolated and non-production. Record exact package/API versions and commands. Do not mutate production lockfiles in a decision-only spike.

**Migration/compatibility concerns.** None until PF4.

**Exit criteria.** A committed audit identifies the chosen v0.1.4 path, explicit rejected alternatives, required migrations and the exact evidence behind the decision.

**Validation record.** `docs/validation/v0.1.4-pf2-mem0-capability-audit.md`.

**Downstream.** PF3 always; PF4 is conditional on the decision.

**Must NOT be implemented early.** Dependency bump, hosted API key wiring, new extraction semantics or replacing YUVI lineage with upstream metadata.

# PF3 — Provider-neutral native People Profile baseline

**Status:** PLANNED ENGINEERING.

**Goal.** Make People/Profile useful with YUVI's own evidence model regardless of PF2's Mem0 decision.

**Why this atom exists.** People/Profile is a main YUVI product feature. It must not disappear when Mem0 Platform is unavailable or when an OSS upgrade is unsafe.

**Preconditions.** PF1 and PF2 decision recorded; v0.1.3 A10.1/A10.3 lineage/context manifests available.

**Existing authority to preserve.** Person/product-store owner; Memory evidence/index owner; A4; journal lineage.

**Exact scope.** Implement one YUVI-native profile provider/projector over eligible lineage-bound Person evidence. It may:

- collect eligible Memory claims for one Person and permitted scopes;
- normalize them into PF1 profile sections;
- preserve conflicts rather than selecting a convenient fact silently;
- use deterministic grouping where possible;
- optionally use a bounded model only to render/structure already eligible evidence, never to invent source IDs, bindings, dates or unsupported facts;
- cache/materialize a versioned snapshot keyed by Person revision + source-set digest + projector version;
- regenerate after source correction/binding revision;
- degrade to partial/unknown when evidence is missing/redacted.

If an LLM renderer is used, every emitted semantic entry must validate against eligible input claim IDs/selectors. Invalid/unreferenced entries are dropped/rejected. The model cannot assign its own provenance or widen audience.

Do not store relationship reliability/trust, YUVI disposition, commitment state, or speculative personality judgments as profile primitives.

**Explicit non-goals.** No Mem0 dependency change; no UI; no profile injection into Cognition yet; no C-series measured relationship/disposition pipeline; no inference from engagement metrics.

**Expected code/docs to inspect.** PF1 contract; Memory claim/search APIs; A10.3 context manifest/retrieval; current People/product services; provider abstractions; correction/amendment paths.

**Required invariants.** PP-I1–PP-I6. Same eligible source set + projector version produces semantically equivalent structured output aside from declared nondeterministic rendering. Raw model prose never becomes a new evidence source for the next regeneration.

**Failure semantics.** Provider/model outage leaves the previous snapshot stale/unavailable according to policy; it does not convert old output into authority. Conflicting source claims remain conflicting. Missing lineage blocks the affected entry.

**Required tests.** Known preference; conflicting preference; third-party hearsay; assistant-generated content; source amendment; Person binding correction; private/group visibility; duplicate evidence; provider failure; snapshot invalidation and regeneration.

**Migration/compatibility concerns.** Existing Memory rows with legacy/incomplete lineage remain limited/legacy and cannot be upgraded into strong profile support merely by inclusion. Do not backfill invented evidence.

**Exit criteria.** A Person with eligible retained evidence receives a grounded profile snapshot without any Mem0 Platform dependency; correction regenerates/invalidates correctly; no unsupported semantic entry survives validation.

**Validation record.** `docs/validation/v0.1.4-pf3-native-profile.md`.

**Downstream.** PF4 and PF5.

**Must NOT be implemented early.** Direct profile edits as truth, relationship learning or profile-driven autonomous initiative.

# PF4 — Conditional Mem0 modernization / profile adapter

**Status:** PLANNED ENGINEERING, CONDITIONAL ON PF2.

**Goal.** Execute only the Mem0 change that PF2 proved worthwhile and safe.

**Why this atom exists.** Upstream Mem0 may provide better retrieval or a useful profile-generation API, but YUVI should adopt it only behind its own contracts and only when it preserves local authority/lineage.

**Preconditions.** PF2 decision; PF3 baseline and tests provide a working fallback/reference.

**Existing authority to preserve.** PF1 profile contract; PF3 native provider; YUVI MemoryProvider and journal lineage; current Person owner.

**Exact scope.** Follow exactly one PF2-selected branch:

### Branch A — `KEEP_PINNED_MEM0`

No dependency upgrade. Add only capability/status plumbing needed to declare that Mem0 remains the Memory backend while PF3 owns profile projection. Close PF4 with a validation record explaining why no production Mem0 change is correct.

### Branch B — `UPGRADE_OSS_MEM0`

Upgrade the local sidecar in a bounded migration atom. Preserve or deliberately replace with tested equivalents:

- local PostgreSQL/pgvector persistence;
- YUVI embedding model/dimensions and private-model behavior;
- finalized idempotent write/reconcile contract;
- `infer=false` semantic admission boundary;
- existing MemoryProvider normalized results;
- health/lifecycle/packaging behavior;
- deletion/history/metadata behavior relied upon by YUVI.

Run migration/compatibility tests against existing stored data or a representative fixture. Do not adopt upstream inference as a new authority by default.

### Branch C — `ADD_OPTIONAL_PLATFORM_PROFILE_PROVIDER`

Add a provider behind PF1's contract without replacing the local Memory backend. It is disabled unless explicitly configured with credentials/consent. Send only the minimum permitted evidence/profile input. Persist job/request identity and provenance sufficient to audit/regenerate. Treat returned profile content as a derived projection subject to PF1 validation, not Person truth.

If the upstream operation is asynchronous, preserve durable request/job identity and explicit pending/failed/unknown states. If idempotency is offered, use and test it; do not infer exactly-once behavior from a local key the remote service does not honor.

Other PF2-selected paths must receive the same authority review before implementation.

**Explicit non-goals.** No mandatory cloud dependency; no automatic migration to upstream generated profiles; no replacement of Journal/Person/P8; no broad Memory Dynamics work.

**Expected code/docs to inspect.** PF2 audit, sidecar/provider/packaging tests, PF1/PF3 profile interfaces, current upstream SDK/API for the pinned selected version.

**Required invariants.** PP-I1–PP-I6 and all v0.1.3 Memory/outbox invariants. A Mem0 failure cannot corrupt Person identity or erase the PF3 fallback.

**Failure semantics.** Failed migration/adapter conformance reverts to PF3/current Memory behavior and blocks PF4 closure for that branch. Do not weaken tests to accept an upgrade.

**Required tests.** Determined by PF2 branch; at minimum provider conformance against PF3 semantic fixtures, correction/regeneration, disclosure, outage/fallback and packaging lifecycle. OSS upgrade branch must run existing Mem0 live/e2e and idempotency/reconciliation suites.

**Migration/compatibility concerns.** One active Memory/profile provider per configured role. No dual write used as a permanent migration strategy. If shadow comparison is needed, it is read-only and time-bounded.

**Exit criteria.** PF2's chosen path is implemented or explicitly closed as no-change, with PF3 remaining a functional fallback/reference and no authority regression.

**Validation record.** `docs/validation/v0.1.4-pf4-mem0-path.md`.

**Downstream.** PF5.

**Must NOT be implemented early.** Upstream feature flags unrelated to People/Profile, cloud sync by default, or broad OSS algorithm migration without PF2 evidence.

# PF5 — People/Profile product surface and A4 projection

**Status:** PLANNED ENGINEERING.

**Goal.** Make the profile visible/useful as a first-class People feature and expose only an authorized bounded projection to Cognition/Character.

**Why this atom exists.** A derived profile that only exists in a backend is not a product feature; ad-hoc prompt concatenation would create a second context authority.

**Preconditions.** PF3; PF4 closed according to its selected path.

**Existing authority to preserve.** A4 canonical context assembler; current People/product UI/store; disclosure policy; P8 field ownership.

**Exact scope.** Add the smallest coherent People/Profile product surface:

- read current Person profile snapshot and status;
- show source/provider/revision/staleness at a useful level;
- allow explicit regenerate/refresh without pretending regeneration changes underlying truth;
- provide evidence/provenance drill-down or references sufficient to inspect why a profile entry exists;
- represent conflicts/unknowns rather than smoothing them away;
- route corrections to the proper underlying Person/Memory/correction authority, then invalidate/regenerate the profile;
- add one A4-owned bounded profile projection/view for Chat/Character/Cognition as appropriate.

If A4 requires a new semantic section (for example `PERSON_PROFILE`), version the canonical context/ABI deliberately and update all intended consumer projections. If existing A4 semantics can represent the profile without conflating relationship context, prefer the smaller change. No provider may inject prompt text directly.

Context rendering must be budgeted. Prefer concise structured/narrative profile information plus relevant evidence over dumping the full profile. Record profile revision/provider/source-set in the context-use manifest.

**Explicit non-goals.** No relationship score UI; no profile editor that directly changes derived values; no QQ-specific People screen; no proactive outreach; no P8 bulk migration.

**Expected code/docs to inspect.** People/product frontend and server routes; A4 context assembly and Character ABI projections; profile provider; Memory/correction APIs; P8 ownership map.

**Required invariants.** PP-I1–PP-I6; A4 remains the only semantic prompt/context assembler; profile information cannot leak from private Person evidence into unauthorized group contexts.

**Failure semantics.** Profile unavailable/stale shows as such and is omitted or marked from context according to policy. UI/provider failure does not block ordinary conversation unless a required disclosure check cannot be made safely.

**Required tests.** UI/read API states; regenerate; correction; conflict; provider outage; A4 projection budget; private/group disclosure; context manifest exact profile revision; existing Chat/Character/Cognition context regression.

**Migration/compatibility concerns.** Existing People entries remain valid. Profile generation may be lazy for existing Persons rather than bulk-running at startup.

**Exit criteria.** A user can inspect a Person profile as a core People feature, correct the underlying source through governed paths, regenerate it, and observe an authorized profile projection in model context with exact lineage/version metadata.

**Validation record.** `docs/validation/v0.1.4-pf5-profile-product.md`.

**Downstream.** PF6.

**Must NOT be implemented early.** Relationship/disposition learning, profile-based user scoring or hidden engagement segmentation.

# PF6 — Cross-surface People/Profile conformance and v0.1.4 closure

**Status:** PLANNED ENGINEERING.

**Goal.** Prove that People/Profile is genuinely core and cross-surface rather than an accidental QQ-only feature.

**Why this atom exists.** QQ is the first large source of Person evidence, which creates a strong temptation to bind profile semantics to QQ account IDs or group behavior.

**Preconditions.** PF5; v0.1.3 QQ adapter remains green; at least one non-QQ identity source is available (for example explicit local Person/controller or voice binding).

**Existing authority to preserve.** Principal→Person binding; QQ thin-surface invariant; voice/controller ownership; A4 disclosure.

**Exact scope.** Run a release conformance matrix covering:

- one Person with a QQ principal and a non-QQ governed binding;
- evidence from both surfaces contributing to the same eligible profile where disclosure permits;
- an unbound QQ principal remaining profile-unknown rather than being guessed into an existing Person;
- private message evidence not leaking into a group profile projection;
- group membership/audience changes;
- binding correction/revocation invalidating affected profile descendants;
- source Memory correction regenerating the profile;
- duplicate/replayed QQ receipts not multiplying profile support;
- chosen Mem0 path outage/fallback;
- restart durability of profile revision/source-set identity;
- context manifest reconstruction of the exact profile snapshot exposed to Cognition.

Publish a concise v0.1.4 closure report and update the implementation baseline.

**Explicit non-goals.** No Discord/Telegram/WeChat rollout requirement; no automatic cross-account identity resolution; no prospective state; no measured relationship learning.

**Expected code/docs to inspect.** PF1–PF5, A12 QQ validation, voice/controller binding tests, A10 lineage/context manifests.

**Required invariants.** PP-I1–PP-I6 plus v0.1.3 I1–I6 where external effects/evidence are involved.

**Failure semantics.** A surface-specific bypass blocks closure. An identity ambiguity remains unresolved, not auto-merged. Provider-specific profile differences that change semantic facts without source support block closure.

**Required tests.** The conformance matrix above as automated integration tests where feasible, plus one pinned real QQ test for the identity/profile path if the authorized environment is available.

**Migration/compatibility concerns.** None beyond documented provider/version differences. Do not create a second profile representation for QQ.

**Exit criteria.** The same Person/Profile contract works across QQ and a non-QQ source; corrections/disclosure/restart behavior are proven; no profile authority lives inside a surface plugin; closure record is committed.

**Validation record.** `docs/validation/v0.1.4-people-profile-closure.md`.

**Downstream.** v0.1.5 M1/M2/E1a and Prospective Life.

**Must NOT be implemented early.** Commitment/expectation scheduling, C-series consolidation, selection learning, revealed disposition.

## 4. Definition of v0.1.4 complete

v0.1.4 is complete only when all of the following are true:

1. People/Profile is a core YUVI domain feature, not a QQ plugin subsystem.
2. Person identity authority remains separate from profile derivation.
3. A provider-neutral native profile works without mandatory hosted Mem0.
4. The Mem0 path is explicitly audited and either safely adopted or deliberately left unchanged.
5. Profile output is grounded in committed eligible evidence with source/audience lineage.
6. Source/binding corrections invalidate dependent profile output.
7. A4 is the only path by which profile information reaches model context.
8. QQ and at least one non-QQ source prove the same Person/Profile contract.
9. No relationship/disposition scalar or Prospective semantics were smuggled into the profile release.

## 5. What v0.1.4 deliberately does not solve

- whether relationship history should accumulate into measured long-term constructs;
- whether YUVI should remember/open obligations across time (v0.1.5);
- whether explicit projections improve behavior enough to justify consolidation (v0.1.6);
- whether learned selection is needed (v0.1.7);
- whether YUVI can form independent interests (later RD/X research);
- full privacy deletion cascade across future research artifacts (PV1);
- automatic identity resolution across unrelated accounts.

The product promise is narrower and testable:

> **YUVI can know who a Person is across governed surface bindings, derive a useful evidence-linked profile of that Person, show where that profile came from, and use only the authorized portion in conversation.**

# v0.1.4 — People & Profile

> **Status:** PLANNED ENGINEERING
>
> **Entry condition:** v0.1.3 Durable Causal History Foundation is closed through A12.2. In particular, A10.1f must already provide the grounded `ProfileProvider` substrate, local profile materialization, People.Model bridge, correction invalidation and aggregate Memory/Profile lineage closure.
>
> **Purpose:** productize People as a first-class cross-surface YUVI capability without rebuilding profile synthesis a second time and without turning QQ, Mem0, an LLM, or the profile itself into identity/relationship authority.

This is a **core product release**, not a plugin release. QQ is the first high-value multi-person surface, but QQ owns only transport normalization. The derived profile substrate is inherited from v0.1.3 A10.1; v0.1.4 is primarily about Person identity/binding, product-facing profile semantics, disclosure/context use, UI and cross-surface closure.

---

## 1. Release outcome

At closure, YUVI can answer four different questions without conflating them:

1. **Who is this principal?** — governed principal → Person binding.
2. **What evidence has YUVI retained about this Person?** — Journal/Memory with provenance and audience.
3. **What profile projection is currently derived from eligible evidence?** — A10.1f `ProfileProvider` / `People.Model` snapshot.
4. **What parts of that profile may be exposed in this current context or UI?** — disclosure/context policy plus People product presentation.

Conceptually:

```text
surface principal
      ↓ explicit/governed binding
    Person
      ↓
committed retained evidence
      ↓
lineage-bound Memory claims
      ↓
A10.1f ProfileProvider
      ↓
People.Model snapshot
      ↓
People UI / A4 context projection
```

A profile is never a replacement for Person identity, raw evidence, relationship measurements, commitments, or charter policy.

---

## 2. Release invariants

### PP-I1 — One Person authority

The governed Person owner remains the authority for Person identity. No profile provider, Mem0 feature, QQ adapter, model output or Memory row can create an authenticated principal→Person binding by itself.

### PP-I2 — Profile is derived and disposable

The semantic profile snapshot inherited from A10.1f can be invalidated and regenerated from eligible retained evidence. Losing the profile materialization must not erase original evidence or Person identity.

### PP-I3 — Facts, Model and relationship adaptation stay separate

Canonical People ownership is:

```text
People
├── Facts
│   └── governed Person fields + grounded Memory/evidence
├── Model
│   └── derived ProfileProvider snapshot
└── Relationship adaptation
    └── later measured/relationship mechanisms
```

A profile field may inform current modeling/context, but it does not become a new fact merely because a model emitted it. Relationship trust/disposition and obligations are not profile primitives.

### PP-I4 — Audience/disclosure never widens

Private evidence cannot become group-visible because it was summarized into a profile. Profile generation/materialization preserves the source scope needed for validation; v0.1.4 disclosure/context projection applies current audience policy before any profile content reaches Cognition/Character or a surface.

### PP-I5 — Corrections invalidate descendants

A source amendment, binding correction or eligible Memory correction invalidates dependent profile/context snapshots. Stale profile output is withheld or explicitly marked stale until regeneration according to policy.

### PP-I6 — Backend neutrality

People/Profile works without requiring Mem0 Platform. The local grounded profile path inherited from A10.1f is the baseline. An upstream hosted profile API may remain an optional provider behind the YUVI contract, never a mandatory cloud dependency or Person authority.

### PP-I7 — Product controls are not inferred profile facts

Authored Person data, controller actions, voice binding and P8 corrections retain their own A10.2 lineage/authority. Derived profile synthesis must not silently replace those writers.

## 3. Inherited Mem0/Profile foundation

v0.1.4 no longer starts with a speculative “does Mem0 have profiles?” decision gate. That question is already relevant during A10.1 because the same Mem0 boundary is being modernized there.

The upstream state recorded during the 2026-09-29 roadmap revision is:

- YUVI's audited local sidecar baseline was pinned to an old OSS `mem0ai` generation using `Memory.from_config(...)`;
- Mem0 Python `2.2.0` / TypeScript `3.3.0` (released 2026-09-23) added **User Profiles** to hosted `MemoryClient` APIs;
- the upstream profile is a structured JSON summary generated from a user's memories according to a project JSON Schema;
- generation is asynchronous and supports request/job status and idempotency keys;
- this release did **not** establish that OSS `Memory.from_config(...)` exposes the same local profile service.

Therefore A10.1f owns the reusable substrate:

```text
ProfileProvider
├── Local grounded materializer        ← required baseline
└── optional Mem0 Platform adapter     ← only if explicitly configured/safe
```

v0.1.4 must consume that substrate rather than reopen the same Memory/provider migration and implement a second profile pipeline.

If the exact Mem0 version/capability changes before implementation, re-verify it in the relevant atom. Upstream package behavior may change; YUVI authority boundaries do not.

# PF1 — People/Profile contract hardening over the A10.1 substrate

**Status:** PLANNED ENGINEERING.

**Goal.** Freeze the product-facing Person/Profile schema and read contract around the already-existing A10.1f provider/materializer.

**Why this atom exists.** A10.1f closes grounded generation and lineage. v0.1.4 still needs a stable product contract distinguishing Person identity, authored fields, derived model fields, stale/partial/conflicting states and presentation metadata.

**Preconditions.** v0.1.3 closed; A10.1f3 validation green; read `identity-and-provenance.md`, `memory-and-lineage.md`, `p8-ownership.md`, A10.2/A10.3 validation and current People/product-store implementation.

**Existing authority to preserve.** Governed Person/product-store ownership; principal→Person binding authority; P8 authored identity/correction ownership; A4 canonical context; A10.1f `ProfileProvider`; Memory as evidence/index only.

**Exact scope.** Define/finalize a versioned People-facing profile view that includes at least:

- authoritative Person reference / revision;
- profile revision and provider/projector version;
- source-set digest/revision;
- generation/freshness state (`CURRENT`, `DIRTY`, `PENDING`, `STALE`, `FAILED`, `UNAVAILABLE`, or equivalent);
- section/field status (`KNOWN`, `PARTIAL`, `CONFLICTING`, `UNKNOWN`, `UNAVAILABLE`, or equivalent);
- evidence references/selectors or a typed evidence summary for every semantic field/section where the underlying A10.1 contract exposes them;
- inherited visibility/audience constraints;
- optional rendered narrative summary separated from structured derived entries.

Candidate sections may include background facts, explicit preferences, communication preferences, interests/common topics, routines/workflows and other ordinary user-profile knowledge. Do not add fields merely because the schema can hold them.

**Explicit non-goals.** No second profile generator; no separate Memory migration; no relationship trust/scalar state; no commitment state; no automatic Person binding; no QQ-owned profile store; no UI.

**Required invariants.** PP-I1–PP-I7. Authored Person fields and derived profile fields cannot silently share writer authority. A provider cannot return authoritative Person bindings.

**Failure semantics.** An ungrounded/unsupported field cannot be promoted into a normal known value. Schema/version mismatch fails visibly rather than coercing old data.

**Required tests.** Type/schema validation; attempted profile overwrite of Person identity; stale/failed/pending provider states; conflicting evidence; private/group audience conflict; provider capability/version mismatch.

**Exit criteria.** One reviewed People/Profile read contract exists in code/docs with tests proving authority separation and compatibility with the A10.1f local provider.

**Validation record.** `docs/validation/v0.1.4-pf1-profile-contract.md`.

**Downstream.** PF2 and PF3.

# PF2 — Governed cross-surface Person binding and correction

**Status:** PLANNED ENGINEERING.

**Goal.** Make a Person stable across desktop, voice, QQ and future surfaces without allowing profile generation or transport identifiers to become identity authority.

**Why this atom exists.** A useful People page requires a reliable answer to “who is this principal?” before profile materialization can be presented as belonging to a Person.

**Preconditions.** PF1; A10.2 identity/controller/voice/P8 lineage closed.

**Existing authority to preserve.** Current Person owner and explicit principal→Person binding authority; A10.2 correction lineage; surface adapters remain transport owners only.

**Exact scope.** Normalize the product-facing Person binding state across supported surfaces. The model should be able to represent at least:

- `BOUND` — governed binding to one Person;
- `UNBOUND` — known principal with no Person binding;
- `AMBIGUOUS` / `REVIEW_REQUIRED` — evidence cannot choose safely;
- `REVOKED` / superseded binding where the current authority model requires it.

Implement correction/rebinding behavior that preserves history rather than rewriting old evidence as if the new Person had always been known. Voice similarity, QQ display names, local access and profile semantic similarity may provide review hints only; none is sufficient authentication by itself unless the identity authority explicitly says otherwise.

**Explicit non-goals.** No face/voice biometric identity system expansion; no automatic account linking from an LLM; no relationship learning; no profile generation change.

**Required tests.** Same Person across two governed surfaces; two principals with same display name; voice/profile hint disagreement; binding correction; old evidence retaining historical binding state; unbound QQ principal; private/group audience preservation.

**Exit criteria.** Product APIs can resolve and display governed Person/binding state across the supported test surfaces without consulting profile content as authority.

**Validation record.** `docs/validation/v0.1.4-pf2-person-binding.md`.

**Downstream.** PF3, PF5, PF6.

# PF3 — People.Model product bridge, freshness and regeneration control

**Status:** PLANNED ENGINEERING.

**Goal.** Expose A10.1f `People.Model` snapshots through stable People product APIs, including stale/dirty/pending/conflict behavior and bounded regeneration control.

**Why this atom exists.** The profile engine may already exist, but the product still needs reliable lifecycle semantics rather than treating any returned JSON as current truth.

**Preconditions.** PF1, PF2; A10.1f profile materialization tests green.

**Existing authority to preserve.** A10.1f owns derived profile materialization; PF2 owns Person binding; product API is a reader/controller, not a new profile writer.

**Exact scope.** Add the People-facing orchestration needed to:

- read the current profile snapshot for a bound Person;
- expose provider/profile revision and freshness state;
- show partial/conflicting/unknown fields without silently flattening them;
- request regeneration through the existing A10.1f provider/job contract;
- coalesce repeated refresh requests and preserve idempotency/job identity where supported;
- invalidate/refetch after source correction or Person binding revision;
- distinguish `profile unavailable` from `Person unknown` and from `insufficient evidence`;
- keep local profile operation functional when a hosted provider is absent/offline.

A hosted Mem0 profile adapter, if A10.1f adopted one, is merely another provider implementation here. PF3 does not reintroduce a Platform dependency.

**Explicit non-goals.** No direct edit-to-truth UI; no second cache that becomes authority; no relationship learning; no broad Memory Dynamics redesign.

**Required tests.** Current/dirty/pending/failed/insufficient states; correction invalidation; duplicate refresh; provider outage; local fallback/baseline; stale revision race; Person rebind while generation is in flight.

**Exit criteria.** Product APIs expose a consistent derived profile lifecycle and regeneration control without bypassing A10.1 lineage/authority.

**Validation record.** `docs/validation/v0.1.4-pf3-profile-product-bridge.md`.

**Downstream.** PF4 and PF5.

# PF4 — Optional Mem0 Platform adapter hardening / capability parity

**Status:** PLANNED ENGINEERING, CONDITIONAL.

**Goal.** If A10.1f retained or introduced a hosted Mem0 User Profiles adapter, harden it for product use without changing the local baseline. If no hosted adapter is selected, close this atom explicitly as `NOT_APPLICABLE` with evidence.

**Why this atom exists.** The upstream hosted profile API may be useful, but it must not become the reason People/Profile exists or the owner of Person truth.

**Preconditions.** PF3; exact upstream SDK/API version frozen for the atom.

**Exact scope when applicable.** Verify and test:

- schema/settings compatibility with the YUVI profile contract;
- asynchronous generation job state mapping;
- idempotency-key reuse on retry;
- pending/failed/insufficient/not-enabled status mapping;
- provider timeout/restart behavior;
- explicit configuration/credentials/consent;
- minimum necessary data disclosure;
- profile key preservation and schema-version mismatch behavior;
- local provider availability when the hosted service is disabled.

Returned hosted profile content remains a derived projection. It cannot create Person bindings, Journal parents, evidence selectors, or authoritative facts that YUVI did not already permit.

**Exit criteria.** Either the optional provider passes parity/authority tests, or the atom records why product v0.1.4 intentionally ships local-only.

**Validation record.** `docs/validation/v0.1.4-pf4-mem0-profile-adapter.md`.

**Downstream.** PF5/PF6, but absence of a hosted adapter does not block them.

# PF5 — People surface and bounded A4 profile projection

**Status:** PLANNED ENGINEERING.

**Goal.** Add the user-visible People/Profile experience and make a bounded, disclosure-safe profile projection available to A4 context.

**Mandatory design gate.** PF5 requires a HUMAN / HIGH-CAPABILITY DESIGN GATE before implementation. A bounded coding model must not invent the People page information architecture, conflict/provenance presentation or visual hierarchy ad hoc. The approved design record must define layout, interaction/state behavior, stale/pending/error presentation, provenance/conflict affordances, responsive behavior and visual constraints.

**Exact scope.** Product surface should support, at minimum:

- Person identity/binding state;
- current profile revision/freshness;
- structured profile sections;
- clear partial/conflict/unknown states;
- evidence/provenance drill-down where safe and useful;
- manual regeneration request/status;
- explicit separation of authored Person fields vs derived profile fields;
- safe handling of unbound/ambiguous principals;
- A4 projection containing only the minimum profile fields allowed for the current audience/context.

Do not expose raw private evidence merely to explain a summary in a broader audience. A4 manifesting remains authoritative for what the execution actually consumed.

**Explicit non-goals.** No direct editing of generated profile text into facts; no trust meters; no personality scores; no automatic social ranking; no engagement optimization.

**Required tests/review.** UI state matrix; disclosure matrix; stale/pending/failed states; conflicting fields; unbound Person; responsive rendering; screenshot/interactive review in addition to automated tests.

**Exit criteria.** People/Profile is usable without requiring hosted Mem0, and the context projection preserves disclosure and provenance boundaries.

**Validation record.** `docs/validation/v0.1.4-pf5-people-surface.md`.

**Downstream.** PF6.

# PF6 — Cross-surface People/Profile closure

**Status:** PLANNED ENGINEERING.

**Goal.** Prove the entire People/Profile contract across QQ plus at least one non-QQ source and close v0.1.4.

**Preconditions.** PF1–PF5; A12 QQ/Snowluma surface available; no unresolved authority regression.

**Required scenarios.** At minimum:

1. one governed Person appears through two surfaces and shares one People identity without duplicating profile authority;
2. an unbound QQ principal remains unbound rather than being auto-linked by semantic similarity;
3. private evidence contributes only where its audience permits;
4. a Memory correction invalidates and regenerates the profile;
5. a Person binding correction preserves old provenance and updates future profile association correctly;
6. profile generation is local when hosted Mem0 is absent;
7. if hosted profile is configured, outage/failure does not erase or replace local Person/Memory authority;
8. profile text cannot feed itself back into Facts/Memory as fresh evidence;
9. A4 manifest identifies the exact profile/source revision used by an execution;
10. QQ remains a thin surface rather than a second People/Profile runtime.

**Failure semantics.** Any cross-person leak, audience widening, unsupported profile claim promoted to fact, or automatic identity binding from profile similarity blocks release closure.

**Exit criteria.** The scenarios pass in automated/fault-injected coverage where possible plus the required real-surface probe; exact provider/version limitations are documented. v0.1.4 then closes.

**Validation record.** `docs/validation/v0.1.4-pf6-cross-surface-closure.md`.

## 4. What v0.1.4 explicitly does not do

v0.1.4 does not introduce:

- a second profile synthesis pipeline separate from A10.1f;
- mandatory Mem0 Platform/cloud usage;
- profile-driven Person authentication;
- relationship trust/disposition learning;
- commitments/prospective state;
- latent self variables;
- engagement-driven social scoring;
- automatic autonomous outreach;
- broad P8 replacement;
- full privacy-deletion/crypto-shredding machinery.

The important scope correction is deliberate:

> **Mem0/Profile materialization is now infrastructure completed alongside A10.1 Memory modernization. v0.1.4 consumes and productizes it; it does not reopen the Memory backend merely to build the same profile function again.**

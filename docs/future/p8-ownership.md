# P8 field-level ownership map

Status: current authority/writer/reader columns are **IMPLEMENTED REALITY** at `ecbb3c5`; future authority and dispositions are a **PRODUCTION ARCHITECTURE DECISION**; every migration is **PLANNED ENGINEERING** after its replacement authority exists. v0.1.3 performs this audit, and A10.2/A10.3 enforce it. Broad P8 migration is **not** v0.1.3 work.

P8 works. The [implementation baseline](implementation-baseline.md#p8-authority-finding) records that no model output path writes P8 identity or relationship state, and that assistant-generated evidence is classified non-authoritative. P8 is therefore not rewritten to match the newer architecture. It becomes a compatibility/projection layer field by field, and it disappears only when replacement authorities actually exist.

The [remaining-core architecture freeze](v0.1.3-authority-effect-context-architecture-freeze.md) freezes the remaining implementation contract. Journal AMENDMENT is reserved; native owner revisions drive corrections/invalidation. Product Person and native P8 stores stay authoritative, and principal→Person product binding remains later work.

**Note: the legacy extractor boundary.** Before A10.1a, an unsupported LLM-generated legacy Memory row could contaminate legacy Memory retrieval while claiming `originRole: user`. Current legacy mode has no semantic `MemoryProvider`, so the reproduced row is not directly reconstructed into a P8 `MemoryEvent`; Runtime receives an unavailable semantic Memory outcome. A10.1a now disables this optional extractor admission path pending committed grounding. More generally, if generated or lineage-bearing Memory is exposed to P8 in future, model-owned `originRole: user` alone must never make it `EXPLICIT_USER_ORIGINATED` or verified evidence. A10.1b–f must preserve that boundary while adding actual ancestry.

## Migration rules

1. **One active writer per field.** For each field above, the current writer is the only writer until a cutover. There are no long-lived dual writes.
2. **Shadow → compare → atomic switch → remove.** The replacement computes in shadow from the same committed inputs. A comparison report (differences, reasons, affected scopes) is reviewed. The reader or writer switches in one versioned change, and the old writer or derivation is then deleted. Rollback restores the previous owner/version as a whole.
3. **No new P8 fields.** New semantics (prospective items, measured projections, selection state) get their own owners. They are not added to P8 “temporarily”.
4. **Replacement first.** No P8 field is deleted before its replacement authority is implemented, tested and has passed the relevant gate ([post-v0.1.3 roadmap](post-v0.1.3-roadmap.md), atom **PM1**).
5. **Corrections keep working.** During any migration, an explicit user correction must still retract or revise the affected meaning within one turn.

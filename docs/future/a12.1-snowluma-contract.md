>
> This document records source-backed SnowLuma transport/effect constraints for YUVI A12.1. It does **not** close A12.1 and does not authorize A12.2 implementation. Live QQ probes remain required only where source cannot establish the exact remote semantics.

## Source-established inbound constraints

### Public `message_id` is not a durable transport identity

SnowLuma's OneBot `message_id` is generated locally as a signed 32-bit value by hashing:

```text
sequence : sessionId : eventName
```

using SHA-1 and reading only the first 32 bits. It is therefore a compatibility handle, not a globally unique QQ message identifier.

Source: `packages/onebot/src/message-id.ts`, `hashMessageIdInt32` at the pinned commit:
https://github.com/SnowLuma/SnowLuma/blob/0591b160fb913131bece693eefd1d0a2ee5a1bbb/packages/onebot/src/message-id.ts#L15-L23

An isolated source-import probe found a same-group collision between distinct sequences. Therefore a future YUVI adapter MUST NOT treat `message_id`, even when scoped by account/group, as proof of duplicate delivery.

### Ordinary inbound messages have no general source-backed dedup guarantee

The inspected `SysMsgDedup` is limited to selected QQ NT **system-message** routes. It uses a process-local set/ring with capacity 1024 and deliberately fails open when the native identity is incomplete or the route is unsupported.

Source:
https://github.com/SnowLuma/SnowLuma/blob/0591b160fb913131bece693eefd1d0a2ee5a1bbb/packages/protocol/src/msg-push/sysmsg-dedup.ts#L12-L83

This does not establish deduplication for ordinary private/group chat messages and does not survive process restart.

### Reconnect/replay

No source-backed guarantee was established that a downstream WebSocket reconnect replays missed ordinary events. Therefore a future adapter must not advertise missed-event replay or infer effect-once inbound processing from reconnect behavior.

### Principal and audience

SnowLuma can expose the current QQ account and message sender through its event surfaces, but those transport identities remain distinct from YUVI `Person` binding. Nickname/card/profile metadata is not authentication.

Group/member lookup can describe current/fetched membership state, but source analysis does not establish it as an exact receipt-time membership snapshot.

## Source-established outbound constraints

### Meaning of a successful ordinary send

For ordinary private/group text send, SnowLuma builds a native `MessageSvc.PbSendMsg` request, waits for its hook transport and a decoded native send response, rejects a nonzero response result, then returns a local `SendMessageReceipt`.

Source:
https://github.com/SnowLuma/SnowLuma/blob/0591b160fb913131bece693eefd1d0a2ee5a1bbb/packages/core/src/bridge/apis/message.ts#L373-L493

A positive SnowLuma/OneBot response therefore establishes only that the inspected SnowLuma path received and accepted a successful decoded native response. Source alone does **not** establish:

- durable QQ server persistence;
- recipient-device receipt;
- human receipt/read.

The exact QQ-side meaning of the positive native reply remains `PROBE_REQUIRED`.

### Returned message identity is not caller idempotency

The returned SnowLuma message identity is locally derived from generated `random`/sequence material. No effective caller-controlled idempotency key was found that the remote QQ effect honors.

Accordingly:

```text
idempotency = UNSUPPORTED
```

for the ordinary future YUVI `send_private_msg` and `send_group_msg` effect contracts unless a later pinned implementation/probe proves otherwise.

### Lost-response reconciliation is unsupported

SnowLuma's hook client has request/ACK/reply correlation and timeouts, but on timeout/connection failure it removes local pending state and throws. No authoritative remote reconciliation path was established for the case in which the QQ effect may have occurred but the reply was lost.

Source:
https://github.com/SnowLuma/SnowLuma/blob/0591b160fb913131bece693eefd1d0a2ee5a1bbb/packages/bridge/src/qq-hook-client.ts#L616-L711

OneBot `get_msg` reads SnowLuma's local stored copy and therefore cannot establish whether an ambiguous response-lost send took effect remotely.

Source:
https://github.com/SnowLuma/SnowLuma/blob/0591b160fb913131bece693eefd1d0a2ee5a1bbb/packages/onebot/src/actions/message.ts#L114-L131

Accordingly:

```text
reconciliation = UNSUPPORTED
```

for a lost-response ordinary send under this pin.

## Required YUVI failure semantics

For SnowLuma ordinary send:

```text
INTENT
  ↓
ATTEMPT
  ↓
SnowLuma / QQ send
```

If the positive native response is observed, record only the level of outcome evidence that response actually supports. Do not upgrade it into recipient/human delivery.

If the call times out, the connection drops, or the response is otherwise lost after the effect may have started:

```text
ATTEMPT exists
OUTCOME = UNKNOWN
NO AUTOMATIC RESEND
```

A timeout is not proof of failure.

This is a hard A9.2/A12.2 constraint unless a future version-pinned adapter gains proven remote idempotency or authoritative reconciliation.

## A12.2 adapter constraints already established

A future thin QQ adapter must not:

- use OneBot `message_id` as a globally unique or collision-free receipt identity;
- suppress ordinary inbound messages solely because the same public `message_id` was observed;
- treat local request/echo IDs as remote idempotency;
- treat `status: ok` as recipient/human delivery;
- auto-resend an ambiguous send after timeout or connection loss;
- use `get_msg` as authoritative lost-send reconciliation;
- treat a fetched group-member list as an exact receipt-time audience snapshot without additional evidence;
- map QQ nickname/card directly to a YUVI `Person`.

If no stronger stable inbound identity is available at the eventual A12.2 boundary, YUVI must prefer duplicate receipt evidence over silently dropping a distinct message because of a 32-bit hash collision.

## Remaining live probes

Live probing is deliberately narrow. It is not needed to re-prove source-established negative capabilities.

`PROBE_REQUIRED`:

1. exact QQ-side meaning of a positive native send reply;
2. native ordinary-message redelivery behavior and native identity stability across reconnect;
3. deliberately lost send reply / connection-loss behavior with independent remote observation;
4. downstream outage/reconnect observations;
5. practical freshness of group membership information;
6. practical multi-account endpoint/account binding.

Any probe must use an explicitly authorized test account/target and retain scrubbed evidence. Failure to run these probes keeps the corresponding capability `UNKNOWN`; it does not justify optimistic defaults.

## Status rule

This document establishes enough source contract for A8/A9 engineering to honor SnowLuma's known limits now.

A12.1 itself remains open until the release plan's required real-surface probe evidence is completed or the unresolved capabilities are explicitly narrowed such that no live guarantee is advertised.

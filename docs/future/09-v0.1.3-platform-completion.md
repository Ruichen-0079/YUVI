# YUVI v0.1.3 — Platform Completion Plan

> **Status:** IN PROGRESS — A0–A3 complete; A4–A13 pending
>
> **Baseline:** `v0.1.2`
>
> **Authority:** current `main`, current source/tests/closure docs, and this plan where it does not conflict with implemented behavior.
>
> **Purpose:** make v0.1.3 the final foundation-building release before YUVI development becomes research-driven for 雏雁 / 鸿雁杯 work.

## 1. Release intent

v0.1.2 closes the current reliability/product campaign: progressive Character streaming, incremental speech, Linux microphone/STT improvements, Portable lifecycle/local-model routing, PostgreSQL/Mem0 isolation, desktop reliability, Live2D reliability, shutdown reliability, and the refreshed YUVI product identity.

v0.1.3 is **not** another broad feature release. It is the platform-completion release.

After v0.1.3:

- the Runtime foundation should be treated as stable experimental infrastructure;
- normal product work should be limited to bug fixes, compatibility, and infrastructure required by an explicit research question;
- Memory Dynamics, adaptive active attention, Character/social-model post-training, and other research work should proceed as research campaigns rather than ordinary feature accumulation;
- YUVI should stop expanding architecture merely because a future capability is conceivable.

The intended boundary is:

```text
v0.1.2
Reliable Product
    ↓
v0.1.3
Platform Complete
    ↓
雏雁 / 鸿雁杯 Research Phase
```

## 2. Global constraints

Every atom must start from current clean `main` after a fresh audit.

For every atom:

- fresh-fetch current `main`;
- inspect local status and worktrees;
- inspect relevant open PRs/issues and current CI;
- inspect recent relevant changes and base drift;
- do not trust stale SHAs in this document;
- do not overwrite unrelated local work;
- do not stack on an unmerged atom unless explicitly required;
- prefer one coherent PR per atom;
- preserve the current Runtime as the sole execution authority;
- preserve current Memory, P8, Provider, Character, Cognition, DesktopSupervisor, and Presentation authorities;
- do not create a second lifecycle authority, provider router, settings store, Memory pipeline, presentation state store, or agent runtime;
- prefer the smallest semantic diff over a cleaner-looking but broader abstraction;
- reuse current seams before adding new managers/services/engines.

The current Phase-6 capability path is an asset, not something to replace. v0.1.3 extends it only where the new bounded-loop/plugin requirements make the extension explicit and testable.

## 3. Explicit non-goals

The following are intentionally **out of scope** for v0.1.3:

- Memory Dynamics research: reinforcement, decay, recurrence dynamics, importance-preserving forgetting;
- learned/adaptive active-attention policy beyond the current bounded proactive foundation;
- Character/social-model post-training integration tied to a not-yet-final checkpoint;
- a generic autonomous agent framework or agent graph;
- a second Runtime or ToolOrchestrator authority;
- browser/computer-control product expansion beyond seams required to prove the capability model;
- humanoid/robot-specific logic in YUVI core;
- ROS-specific coupling in Runtime;
- another broad WebUI/desktop visual redesign;
- speculative Temporal/Continuity subsystem expansion;
- rebuilding Windows persistence ownership as a parallel architecture.

These may be implemented later only when required by the research campaign or a proven product gap.

# Phase I — Bounded Runtime / Capability Loop

## ATOM A1 — Canonical Interaction-Round Contract

Completed: [contract, containment state, and validation](../interaction-round.md). Multi-round execution is closed by A2 below.

### Goal

Generalize the already-proven one-capability Cognition path into an explicit bounded interaction-round contract without introducing a second orchestration authority.

### Required semantics

Model one round as a provider-neutral decision such as:

```text
InteractionRound
├─ COMPLETE
├─ REQUEST_CAPABILITY
└─ CONTINUE
```

The exact wire shape must follow current source and provider-neutral conventions rather than this pseudocode.

Define explicit bounded state for:

- reasoning round count;
- capability-call count;
- deadline/time budget where applicable;
- cancellation;
- Runtime execution identity;
- terminal completion/failure.

### Constraints

- Runtime remains the hard-loop containment authority.
- Cognition may propose semantic continuation/capability need but does not execute effects.
- MCP/plugin layers perform only already-admitted invocations.
- no `AgentGraph`, generic planner runtime, or parallel orchestration service.

### Exit criteria

A provider-neutral, testable round contract exists and can represent the current one-capability behavior without weakening current containment semantics.

## ATOM A2 — Bounded Multi-Round Runtime Loop

Completed: [bounded-loop implementation and containment evidence](../validation/v0.1.3-a2-bounded-loop.md).

### Goal

Extend the current one-capability round-trip into a bounded loop inside the existing Runtime authority.

### Target flow

```text
Cognition
   ↓
COMPLETE ─────────────────────────→ finish
   │
REQUEST_CAPABILITY
   ↓
Runtime admission
   ↓
capability execution
   ↓
normalized observation
   ↓
Cognition
   ↓
... bounded by Runtime budget
```

### Required behavior

- explicit hard maximum reasoning rounds;
- explicit hard maximum capability calls;
- user cancellation propagates through provider and capability work;
- stale results cannot commit after replacement/cancellation;
- shutdown/sealing/draining semantics remain authoritative;
- no phantom continuation after a terminal result;
- capability/tool failure is normalized rather than fabricated as success;
- retries, if any are later admitted, must be explicit and must not create hidden loop expansion.

Initial limits should remain conservative and configurable only through the existing configuration authority.

### Exit criteria

A complete bounded Cognition → capability → Cognition loop exists with containment, cancellation, failure, and lifecycle tests.

## ATOM A3 — Tool-Result Adjacency and Execution Evidence

Completed: [adjacency, execution evidence, and persistence rules](../validation/v0.1.3-a3-execution-evidence.md).

### Goal

Make capability continuation context deterministic and safe for future providers and experiments.

### Required semantics

Preserve local adjacency:

```text
assistant/cognition capability request
capability observation
assistant/cognition continuation
```

No unrelated Memory injection, system reminder, presentation event, or arbitrary context section may split a capability request from its corresponding observation inside the provider-facing continuation structure.

Define clearly:

- which tool/capability artifacts are execution evidence only;
- which artifacts may be persisted in conversation history;
- which artifacts are user-visible;
- which artifacts may be projected into later context;
- that capability success is **not** automatically Memory truth, P8 truth, or relationship truth.

### Exit criteria

Adjacency, evidence projection, and persistence rules are explicit, provider-neutral, and covered by regression tests.

# Phase II — Canonical Context and Cache Semantics

## ATOM A4 — Canonical Context Assembly

### Goal

Create one authoritative context assembly path before research work starts depending on stable experimental conditions.

### Scope

Unify the currently authorized context components into a canonical ordered structure. The exact order must be derived from current implementation and measured behavior, but the assembly authority must be singular.

Expected classes include:

```text
Identity / Persona / Relationship projection
stable system/product policy
capability descriptions / model-facing contracts
Direct Context / recent conversational context
retrieved Memory evidence
current multimodal/user input
tool-local continuation evidence
```

### Constraints

- no separate Chat context builder and Cognition context builder that drift semantically;
- provider adapters may serialize the canonical structure but may not invent product semantics;
- Memory remains evidence rather than persona truth;
- tool continuation may use a local continuation projection while preserving A3 adjacency.

### Exit criteria

All supported production paths derive provider-facing context from one canonical semantic assembly boundary or an explicitly documented projection of it.

## ATOM A5 — Stable-Prefix and Cache Boundary

### Goal

Define cache-stable versus turn-volatile context semantics without coupling YUVI to one provider cache implementation.

### Stable candidates

Examples that may belong to a stable prefix where current source allows:

```text
Identity
Persona
stable policies
stable capability descriptions/schemas
static provider-neutral instructions
```

### Volatile candidates

```text
recent turns
retrieved Memory evidence
current user input
current perception
capability observations
```

### Constraints

- this atom defines semantic stability, not a provider-specific cache hack;
- DeepSeek/OpenAI-compatible/local llama.cpp caching can later consume the same semantic boundary;
- changing cache layout must not change product meaning;
- prefix identity/versioning must be explicit enough for experiments to reproduce context conditions.

### Exit criteria

Stable-prefix identity and volatile context boundaries are explicit and testable, with no provider-specific authority leak.

# Phase III — Plugin and Capability Boundary

## ATOM A6 — Minimal Plugin Manifest and Lifecycle

### Goal

Introduce the smallest plugin boundary required for external surfaces and capabilities without creating a marketplace framework.

### Minimal contract

A plugin may declare metadata such as:

```text
id
version
compatibility
declared capabilities
optional presentation/input surfaces
```

Lifecycle should remain minimal:

```text
discover
load
start
stop
dispose
```

The exact API must follow current Runtime and server composition patterns.

### Constraints

- plugins do not own Runtime execution;
- plugins do not create an independent Memory or provider pipeline;
- plugin lifecycle cannot outlive or bypass Runtime/desktop lifecycle ownership;
- plugin loading failure must be bounded and diagnosable.

### Exit criteria

A minimal plugin can be discovered, loaded, started, stopped, and disposed without becoming a second product runtime.

## ATOM A7 — Runtime-Owned Capability Registry

### Goal

Allow plugins to expose executable capabilities through the existing semantic capability model.

### Intended shape

A plugin may provide a concrete implementation associated with a provider-neutral semantic capability description. Conceptually:

```text
Plugin
  ↓ concrete registration
Capability Registry
  ↓ semantic inventory
Cognition
  ↓ REQUEST_CAPABILITY
Runtime admission
  ↓ concrete mapping
Plugin executor
```

### Important rule

Models should not become coupled to arbitrary plugin function names or transport details.

Preserve the Phase-6 design principle:

```text
semantic capability reference
        ↓
Runtime-owned mapping
        ↓
concrete implementation
```

### Exit criteria

At least one plugin-provided capability is discoverable through the canonical inventory and executable only after Runtime admission.

## ATOM A8 — Capability Effect Classification and Admission

### Goal

Create an explicit policy seam for extending beyond read-only capabilities while keeping effect authority centralized.

### Minimum taxonomy

The exact enum may change, but semantics should cover at least:

```text
READ_ONLY
REVERSIBLE
MUTATING
EXTERNAL_SIDE_EFFECT
```

Examples:

```text
read local text        READ_ONLY
open/reveal local view REVERSIBLE
modify local file      MUTATING
send external message  EXTERNAL_SIDE_EFFECT
robot/environment move EXTERNAL_SIDE_EFFECT / environment-facing
```

### Constraints

- classification is not authorization by itself;
- Runtime owns final admission;
- high-risk/environment-facing execution may remain disabled in v0.1.3;
- the purpose is to make future policy explicit, not to expose every effect class immediately.

### Exit criteria

Effect classification exists, Runtime admission consumes it, and unsupported classes fail closed.

## ATOM A9 — First External-Surface Plugin: QQ / Snowluma Adapter

### Goal

Prove that the plugin boundary supports a real external interaction surface without forking YUVI product logic.

### Target architecture

```text
YUVI Runtime
   ↓
Plugin contract
   ↓
QQ / Snowluma adapter
   ↓
external chat surface
```

### Required behavior

- inbound external message enters the canonical Runtime path;
- outbound YUVI response returns through the adapter;
- explicit identity/conversation mapping;
- reconnect/restart behavior is bounded;
- adapter lifecycle follows plugin lifecycle;
- no second chat Runtime;
- no external-surface-only Memory or persona semantics.

### Exit criteria

The adapter works end to end and demonstrates that future external surfaces can remain thin adapters over the same Runtime.

# Phase IV — Cross-Platform Foundation

## Platform policy

v0.1.3 adopts:

> **Linux-first, cross-platform-safe, release-parity.**

Linux remains the Tier-1 reference development platform.

Windows and macOS must remain continuously buildable and must reach defined release parity for core product behavior, but they do not need the same frequency of manual testing during high-intensity Linux development.

Three long-lived platform branches are explicitly rejected. All supported platforms follow `main`.

## ATOM A10 — Platform Boundary Audit

### Goal

Concentrate OS-specific behavior behind existing or minimal platform seams so Linux-first development does not continuously rot Windows/macOS.

### Audit targets

```text
process spawn / child ownership
path resolution
config/cache/data directories
runtime child lifecycle
localhost/port binding
tray
window flags
always-on-top
click-through/locked windows
drag-and-drop
file picker
microphone/audio enumeration
Portable/install paths
shutdown/orphan cleanup
```

### Constraints

- do not perform a broad platform-framework rewrite;
- use existing seams first;
- common Runtime semantics must not depend on Unix-only APIs;
- OS-specific translation belongs at the platform edge.

### Exit criteria

Known OS-specific behaviors are either portable in common code or isolated behind explicit platform boundaries.

## ATOM A11 — Windows Core Bring-Up

### Goal

Restore Windows as an active supported target without recreating a second persistence/lifecycle architecture.

### Core parity target

At minimum verify:

```text
Desktop starts
Runtime starts
Chat works
Reasoning/Cognition works
Memory can connect/use the supported configured path
Provider configuration works
basic STT/TTS path works
basic Live2D/desktop window path works
tray works
shutdown/orphan cleanup works
```

### Persistence rule

Do **not** rebuild Windows-specific packaged PostgreSQL ownership merely for parity. External/configured PostgreSQL/Mem0 may remain the supported Windows path until a later proven product need justifies more packaging work.

### Exit criteria

Windows reaches documented Core Parity and produces a reproducible build/smoke result from current `main`.

## ATOM A12 — macOS Core Bring-Up and Three-Platform CI

### Goal

Bring macOS into the same support policy and prevent future platform drift through CI.

### Core parity target

Match the same core-product expectations as Windows where platform APIs allow, with explicit capability flags for features that are unavailable or deferred.

### CI policy

Linux should run the strongest gate, including the full supported test/build/package path.

Windows and macOS should run at least:

```text
lint / typecheck
unit tests
Rust compile/tests where applicable
Tauri build
platform-specific compile checks
```

Where practical, scheduled or release-candidate smoke should cover actual packaged launch behavior.

### Capability lag

Platform-specific features may expose explicit capability state instead of fake support, for example conceptually:

```text
transparent_window: true
global_hotkey: false
desktop_observation: false
```

Experimental Linux-only capabilities may remain Linux-only until promoted intentionally.

### Exit criteria

Every PR can detect obvious Windows/macOS portability regressions, while manual high-frequency development remains Linux-first.

# 4. Post-v0.1.3 research boundary

v0.1.3 deliberately leaves the following as research work rather than silently shipping them into the baseline.

## Track A — Social / Character Model Post-Training

Research question:

> Can a relatively small open-weight model be post-trained specifically for persistent social interaction, while serious reasoning remains delegated to a separate Cognition model?

YUVI v0.1.3 only needs a stable replaceable Chat/Character provider boundary. Training datasets, SFT/DPO/preference work, checkpoint comparison, and human evaluation belong to the research campaign.

## Track B — Long-Term Memory Dynamics

Research question:

> How should long-term companion memories strengthen, decay, recur, be superseded, and preserve low-frequency but high-importance evidence over extended interaction?

The static v0.1.3 Memory path is the baseline for later controlled comparison.

## Track C — Adaptive Active Attention

Research question:

> When should a persistent companion proactively speak, wait, or remain silent, and how should that policy adapt to a user's long-term interaction habits?

The current bounded proactive foundation remains the baseline. Learned/adaptive policy changes belong to the research campaign.

These tracks may share infrastructure, but they should not be merged into one uncontrolled product campaign.

# 5. Embodiment and external devices

v0.1.3 should make YUVI capable of supporting future remote embodiments without embedding device-specific logic into Runtime.

A humanoid robot, mobile client, or other device should be treated as an external surface/capability provider:

```text
YUVI Runtime / Server
        ↓ network
plugin / adapter boundary
        ↓
robot or device middleware
        ↓
real-time control / safety
```

YUVI may own high-level conversation, cognition, Memory, persona, and admitted high-level actions.

YUVI must not become the hard real-time motor/safety controller. Device-local safety, motion control, emergency stop, collision avoidance, and equivalent safety envelopes remain outside YUVI Runtime.

No robot-specific core architecture should be added until a real external implementation and stable interface exist.

# 6. Final product-development rule

After v0.1.3, before adding a major feature to `main`, ask:

> Does this change fix a proven platform defect, satisfy a concrete supported-platform requirement, or directly support an explicit research hypothesis / experiment?

If the answer is no, it should normally remain out of the product baseline.

That boundary is intentional. YUVI should stop growing by feature accumulation and begin functioning as a stable experimental platform for long-term human–AI interaction research.
